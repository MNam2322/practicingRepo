# 6.6 HTTP

> **Quick look.** HTTP, the request/response protocol behind the web and almost every API.
>
> - A request has a method, path, headers and optional body; a response has a status code, headers and body.
> - GET and HEAD are safe; PUT and DELETE are idempotent; POST is neither, so it can't be retried blindly.
> - 4xx means the client is at fault, 5xx the server.
> - Cookies add state; Cache-Control and ETags avoid repeated transfers.
> - HTTP/1.1 keeps connections open, HTTP/2 multiplexes many requests on one connection, HTTP/3 runs over QUIC.
> - A network call costs roughly a million times a method call, which drives most API design.


### The big picture

HTTP is the language of the web. Every page load, every web API call, every mobile app talking to its server and most messages between cloud services use it. At heart it is simple: a client sends a request, like placing an order at a counter, and the server sends back one response. Both are, in their basic form, just lines of text in a fixed shape.

This chapter shows that text directly, by building a tiny web server on the TCP connections from TCP and UDP (6.3), then compares it with what `HttpClient` does for you. It covers the parts of every request and response, what methods and status codes mean, how caching and cookies work, how HTTP/2 and HTTP/3 made it faster, and the proxies and load balancers that sit in between. It ends Part 6, and it is the foundation for building backends in Part 8.

### Skip check

Answer each question in your head, then read the answer under it. If you got all of them, you can skip this chapter.

**1. What are the parts of an HTTP request?**

> A request line with the method, the path and the version, such as `GET /flights HTTP/1.1`. Then header lines of the form `Name: value`. Then a blank line. Then an optional body.

**2. Which HTTP methods are safe, and which are idempotent?**

> GET and HEAD are safe: they shouldn't change anything. PUT and DELETE are idempotent: doing them twice has the same effect as once. POST is neither, which is why retrying a POST can create duplicates.

**3. What is the difference between 401 and 403?**

> 401 Unauthorized means "I don't know who you are": log in or send valid credentials. 403 Forbidden means "I know who you are, and you may not do this".

**4. What do 502, 503 and 504 usually point to?**

> A problem behind a proxy or load balancer. 502 Bad Gateway: it got an invalid answer from the server behind it. 503 Service Unavailable: the service is overloaded or down. 504 Gateway Timeout: the server behind it didn't answer in time.

**5. What does Cache-Control: max-age=60 tell a client?**

> It may reuse this response for up to 60 seconds without asking the server again.

**6. How do HTTP/1.1, HTTP/2 and HTTP/3 differ?**

> HTTP/1.1 is text, with one request at a time on each connection. HTTP/2 is binary and runs many requests at once over one TCP connection. HTTP/3 does the same over QUIC, on UDP, so one lost packet doesn't stall every request.

**7. What is the default timeout of HttpClient?**

> 100 seconds. That is far too long for most service-to-service calls; set a timeout that fits each call, and pass cancellation tokens.

**8. What is a cookie?**

> A small piece of data a server asks the browser to store, with a `Set-Cookie` header, and which the browser then sends back on later requests to that site. It is how a stateless protocol remembers a logged-in user.

### Requests and responses

**HTTP**, the Hypertext Transfer Protocol, was created by Tim Berners-Lee in 1989 and 1990 for the first web browser and server. Its model has barely changed. A client opens a connection to a server and sends an **HTTP request**. The server sends back one **HTTP response**. That is the whole conversation.

HTTP is a **stateless protocol**: each request stands alone, and the server isn't required to remember anything about earlier ones. That makes servers simple to scale, because any server can answer any request. Remembering things across requests, such as who is logged in, is built on top with cookies and tokens.

HTTP runs on TCP, and with TLS it becomes HTTPS, as TLS (6.5) described. In HTTP/1.1, the version this chapter shows first, requests and responses are plain text that you can read and type by hand.

### Addresses: URLs

A request is aimed at a resource named by a **URL**, a uniform resource locator. `https://api.example.com:8443/flights/BA117?date=2026-09-28#status` has these parts:

- `https` is the scheme: which protocol to use.
- `api.example.com` is the host, looked up in DNS as DNS (6.4) explained.
- `8443` is the port. When it is left out, it is 443 for `https` and 80 for `http`.
- `/flights/BA117` is the path: which resource on that server.
- `?date=2026-09-28` is the query string: extra parameters, as name-value pairs separated by `&`.
- `#status` is the fragment: a position within the page. The browser keeps it and never sends it to the server.

Characters with special meanings, such as spaces, `&` and `?`, must be percent-encoded when they appear inside a value, as Text is numbers too (1.3) showed. In .NET, build URLs with `Uri` and `Uri.EscapeDataString` rather than joining strings.

### What a request looks like

This is a complete HTTP/1.1 request, exactly as it is sent:

```text
GET /flights/BA117?date=2026-09-28 HTTP/1.1
Host: api.example.com
Accept: application/json
User-Agent: FlightBoard/2.1
```

The first line is the request line: the method, the path with its query string, and the protocol version. Next come the headers, one per line. A blank line ends the headers. A request with data to send, such as a form or a JSON document, puts it after the blank line as the **message body**. Lines end with a carriage return and line feed, the CRLF pair from Storage and files (1.6).

`Host` is required, because one server address often serves many sites, just as SNI tells TLS which certificate to use.

### Methods

The **HTTP method** says what the client wants to do with the resource.

GET fetches a resource. HEAD fetches only the headers, not the body. POST submits data to be processed, typically creating something. PUT replaces a resource with the one in the body. PATCH changes part of a resource. DELETE removes it. OPTIONS asks which methods are allowed, and browsers use it for checks covered in Common web vulnerabilities (10.4).

Methods come with promises that other software relies on. A **safe method**, GET or HEAD, shouldn't change anything on the server, so browsers, crawlers and caches may send it freely. An idempotent method has the same effect however many times it is repeated, as Errors and exceptions (2.8) explained. PUT and DELETE are idempotent, as are the safe methods. POST and PATCH usually aren't. That is why proxies and HTTP clients retry GETs automatically after a network error, but never POSTs, and why a "Buy" button should never be a GET link.

### What a response looks like

A response has the same shape:

```text
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 31
Cache-Control: max-age=60

{"flight":"BA117","gate":"B12"}
```

The status line holds the version, a numeric **status code** and a short reason phrase. Headers follow, then a blank line, then the body.

### Status codes

The first digit of a status code gives its class.

**2xx: success.** 200 OK. 201 Created, usually with a `Location` header giving the new resource's URL. 204 No Content: it worked, and there is no body.

**3xx: redirection.** 301 Moved Permanently and 308 Permanent Redirect say the resource has a new URL for good. 302 Found and 307 Temporary Redirect send the client elsewhere for now. 304 Not Modified tells the client its cached copy is still good.

**4xx: the client's fault.** 400 Bad Request: the request was malformed or invalid. 401 Unauthorized: the client isn't authenticated. 403 Forbidden: authenticated, but not allowed. 404 Not Found. 409 Conflict: the request clashes with the resource's current state. 422 Unprocessable Content: well-formed, but it fails validation. 429 Too Many Requests: slow down, often with a `Retry-After` header.

**5xx: the server's fault.** 500 Internal Server Error: something failed unexpectedly. 502 Bad Gateway, 503 Service Unavailable and 504 Gateway Timeout usually come from a proxy or load balancer about the servers behind it, as the section on proxies below explains.

The distinction between 4xx and 5xx matters in practice. Retrying a 4xx won't help without changing the request. Retrying a 503 after a pause might.

### Headers

**HTTP headers** carry everything about a message except its body. There are hundreds; a handful appear everywhere.

`Content-Type` says what the body is, as a media type: `application/json`, `text/html; charset=utf-8`, `image/png`. The charset matters for text, for the reasons in Text is numbers too (1.3). `Accept` says which types the client can handle. `Content-Length` gives the body's size in bytes. `Authorization` carries credentials, such as a token. `User-Agent` names the client software. `Location` points to a new or moved resource. `Cache-Control` and `ETag` control caching, below. `Set-Cookie` and `Cookie` carry cookies.

Header names are case-insensitive. Custom headers are allowed; the old convention of starting them with `X-` is no longer recommended.

### Where the body ends

HTTP runs on TCP's byte stream, which has no message boundaries, so HTTP must say where each body ends: the framing problem from TCP and UDP (6.3). There are two ways. `Content-Length` gives the exact number of bytes. **Chunked transfer encoding**, marked by the `Transfer-Encoding: chunked` header, sends the body in pieces, each preceded by its own length, with a zero-length piece at the end. Chunked encoding lets a server start sending before it knows the total size, for example while generating a large report. Bodies can also be compressed with gzip or Brotli, from Storage and files (1.6), announced by `Content-Encoding`.

### Seeing it for real

This program builds a tiny web server directly on a TCP connection, to show that HTTP really is text in a fixed shape. It then talks to it twice: once by writing a request by hand, and once with `HttpClient`.

```csharp
// http.cs — run with: dotnet run http.cs
using System.Linq;
using System.Net;
using System.Net.Sockets;
using System.Text;

// A tiny HTTP server built directly on TCP
var listener = new TcpListener(IPAddress.Loopback, 0);
listener.Start();
int port = ((IPEndPoint)listener.LocalEndpoint).Port;
_ = Task.Run(async () =>
{
    while (true)
    {
        using TcpClient connection = await listener.AcceptTcpClientAsync();
        using NetworkStream stream = connection.GetStream();
        using var reader = new StreamReader(stream, Encoding.ASCII, leaveOpen: true);
        string requestLine = await reader.ReadLineAsync() ?? "";      // "GET /flights/BA117 HTTP/1.1"
        while (!string.IsNullOrEmpty(await reader.ReadLineAsync())) { }   // skip headers up to the blank line
        string path = requestLine.Split(' ').ElementAtOrDefault(1) ?? "";
        (int status, string reason, string body) = path == "/flights/BA117"
            ? (200, "OK", "{\"flight\":\"BA117\",\"gate\":\"B12\"}")
            : (404, "Not Found", "{\"error\":\"no such flight\"}");
        byte[] bodyBytes = Encoding.UTF8.GetBytes(body);
        string head = $"HTTP/1.1 {status} {reason}\r\n" +
                      "Content-Type: application/json; charset=utf-8\r\n" +
                      $"Content-Length: {bodyBytes.Length}\r\n" +
                      "Cache-Control: max-age=60\r\n" +
                      "Connection: close\r\n" +
                      "\r\n";                                             // the blank line: headers end, body follows
        await stream.WriteAsync(Encoding.ASCII.GetBytes(head));
        await stream.WriteAsync(bodyBytes);
    }
});

// 1. A request written by hand, exactly as a browser would send it
using (var tcp = new TcpClient())
{
    await tcp.ConnectAsync(IPAddress.Loopback, port);
    NetworkStream stream = tcp.GetStream();
    string request = $"GET /flights/BA117 HTTP/1.1\r\nHost: 127.0.0.1:{port}\r\nAccept: application/json\r\n\r\n";
    await stream.WriteAsync(Encoding.ASCII.GetBytes(request));
    Console.WriteLine(await new StreamReader(stream).ReadToEndAsync());  // the server closes the connection when done
}
// HTTP/1.1 200 OK
// Content-Type: application/json; charset=utf-8
// Content-Length: 31
// Cache-Control: max-age=60
// Connection: close
//
// {"flight":"BA117","gate":"B12"}

// 2. The same server through HttpClient, which writes and parses all of that for you
using var http = new HttpClient { BaseAddress = new Uri($"http://127.0.0.1:{port}"), Timeout = TimeSpan.FromSeconds(5) };
foreach (string path in new[] { "/flights/BA117", "/flights/XX999" })
{
    using HttpResponseMessage response = await http.GetAsync(path);
    string body = await response.Content.ReadAsStringAsync();
    Console.WriteLine($"{path}: {(int)response.StatusCode} {response.StatusCode}, " +
                      $"cache {response.Headers.CacheControl?.MaxAge?.TotalSeconds} s, body {body}");
}
// /flights/BA117: 200 OK, cache 60 s, body {"flight":"BA117","gate":"B12"}
// /flights/XX999: 404 NotFound, cache 60 s, body {"error":"no such flight"}
```

A real server, such as ASP.NET Core's Kestrel, does far more: it handles many connections at once, keeps connections open between requests, supports HTTP/2 and HTTP/3, limits request sizes and defends against malformed input. But on the wire, every HTTP/1.1 exchange looks like this.

### Remembering things: cookies

Because HTTP is stateless, a server that wants to recognize a returning browser gives it a **cookie**: a small named value sent in a `Set-Cookie` header. The browser stores it and sends it back in a `Cookie` header on every later request to that site. A login usually sets a cookie holding a session id or an encrypted token.

Cookie attributes control where they go. `Secure` sends a cookie only over HTTPS. `HttpOnly` hides it from JavaScript in the page, which limits the damage of cross-site scripting. `SameSite` limits whether other sites can trigger requests that carry it. `Expires` or `Max-Age` sets how long it lasts. APIs used by other programs, rather than browsers, usually send a token in the `Authorization` header instead, as Authentication and authorization (10.2) explains.

### Caching

The fastest request is one never made. HTTP has caching built in, and browsers, proxies and CDNs all follow the same rules.

`Cache-Control` in a response sets them. `max-age=60` means "reuse this for 60 seconds". `no-store` means "never store this", right for anything personal or sensitive. `no-cache` means "you may store it, but check with me before each reuse". `private` means only the user's own browser may keep it, not shared caches. `public` allows shared caches.

When a cached copy expires, the client doesn't have to download everything again. The server can give each version of a resource an **ETag**: an identifier that changes whenever the content changes. The client makes a **conditional request**, sending `If-None-Match` with the ETag it has. If nothing changed, the server replies `304 Not Modified` with no body, and the client keeps using its copy. That costs a round trip but saves the transfer.

A **CDN**, content delivery network, is a service with caching servers in many cities. Users are sent to the nearest one, which serves cached responses, such as images, scripts and even API responses, without a trip to the origin server.

### Connections and versions

HTTP/1.0 opened a new TCP connection for every request, paying a handshake each time. HTTP/1.1 made **persistent connections** the default: the connection stays open for further requests, unless either side sends `Connection: close`. That is what makes the connection pools in TCP and UDP (6.3) possible.

HTTP/1.1 still handles one request at a time per connection. A slow response holds up every request queued behind it, a form of the head-of-line blocking from the same chapter. Browsers work around it by opening about six connections per site.

**HTTP/2**, standardized in 2015, keeps the same methods, headers and status codes, but changes how they travel. Messages become binary frames. Many requests and responses run at the same time over one TCP connection, as separate streams, interleaved. Headers are compressed, which matters because the same headers repeat on every request. `HttpClient` uses HTTP/2 when the server supports it, and gRPC, a popular protocol for calls between services, is built on it.

HTTP/2 over TCP still has one weakness: a lost packet stalls every stream on the connection, because TCP delivers bytes in order. **HTTP/3**, standardized in 2022, runs over **QUIC**, a transport protocol built on UDP. QUIC provides reliable, ordered delivery per stream, so a lost packet only delays its own stream. It combines the connection and TLS handshakes into one round trip, and a connection can survive a change of network, such as a phone moving from Wi-Fi to mobile data. Most major sites and browsers support it.

### Proxies, gateways and load balancers

Requests often pass through servers that act on behalf of others.

A **reverse proxy** sits in front of one or more servers and receives requests for them. It can terminate TLS, as TLS (6.5) described, compress responses, cache, and route different paths to different backends. Nginx, Envoy, YARP for .NET and cloud application gateways are reverse proxies.

A **load balancer** is a reverse proxy whose main job is spreading requests across several identical servers, checking their health and sending traffic only to healthy ones.

When something behind the proxy fails, the proxy generates the error. It reports 502 if the server sent back something invalid or closed the connection, 503 if no healthy server is available, and 504 if the server didn't answer in time. When you see these, look at the servers behind the proxy, not the proxy itself.

A proxy hides the original client from the server behind it: the server sees the proxy's address. Proxies pass the original along in headers, `X-Forwarded-For` and `X-Forwarded-Proto`, or the standard `Forwarded` header. ASP.NET Core's forwarded headers middleware reads them, but should only trust them from known proxies, because anyone can send those headers.

### HttpClient in practice

In .NET, `HttpClient` is the client for HTTP. A few habits matter.

Reuse clients, or create them with `IHttpClientFactory`, so connections are pooled and DNS changes are picked up, as TCP and UDP (6.3) and DNS (6.4) explained. Set a timeout per call that suits it; the default of 100 seconds is far too long for most calls between services. Pass a `CancellationToken`, so abandoned requests stop.

Check the status. `EnsureSuccessStatusCode()` throws for anything outside 2xx; otherwise, inspect `StatusCode` and decide. For large downloads, pass `HttpCompletionOption.ResponseHeadersRead` and read the body as a stream, instead of loading it all into memory. Add retries and timeouts for transient failures with `Microsoft.Extensions.Http.Resilience`, retrying only idempotent requests, as Reliability (12.5) explains.

### In short

HTTP is a stateless request-and-response protocol. A request has a method, a URL path, headers, a blank line and an optional body; a response has a status code, headers and a body. GET and HEAD are safe, PUT and DELETE are idempotent, and POST is neither, so only some requests can be retried safely. Status codes say whether the client or the server is at fault. Cookies add memory, and caching headers with ETags avoid repeated transfers. HTTP/1.1 keeps connections open, HTTP/2 runs many requests over one connection, and HTTP/3 moves to QUIC over UDP.

### What goes wrong

**Changing data with GET.** A crawler, a link preview or a prefetching browser follows a "delete" link and deletes things. Use POST, PUT or DELETE for anything that changes state.

**Retrying POSTs blindly.** A timed-out order is retried and placed twice. Retry only idempotent requests, or give POSTs an idempotency key the server checks.

**Wrong status codes.** An API that returns 200 with an error message in the body breaks caches, retries and monitoring that rely on status codes. Use the real codes.

**Caching personal data.** A response with a user's details and no cache rules is stored by a shared proxy and shown to someone else. Mark such responses `private` or `no-store`.

**Default timeouts.** A service waits 100 seconds for a dead dependency while its own callers time out. Set timeouts per call, shorter than the caller's.

**Loading huge bodies into memory.** Reading a 2 GB download with `ReadAsStringAsync` exhausts memory. Stream it.

**Trusting forwarded headers from anyone.** An attacker sends a fake `X-Forwarded-For` and bypasses an address-based rule. Only accept forwarded headers from known proxies.

### Cost model

A request on a warm, pooled connection costs one round trip plus server time. A request on a new HTTPS connection adds a TCP handshake and a TLS handshake, two more round trips, or one with HTTP/3. HTTP/1.1 headers are often 500 bytes to 2 KB per request, repeated every time, which HTTP/2 and HTTP/3 compress. A cached response costs nothing on the network; a 304 revalidation costs a round trip but no body. For APIs, the number of round trips and the size of JSON bodies usually matter more than anything else.

### Key terms

- **HTTP**: Hypertext Transfer Protocol: the request-and-response protocol of the web.
- **Stateless protocol**: A protocol where each request stands alone, with no required memory of earlier ones.
- **HTTP request**: A message from client to server: method, path, headers and an optional body.
- **HTTP response**: A message from server to client: status code, headers and an optional body.
- **URL**: Uniform resource locator: a scheme, host, optional port, path, query and fragment naming a resource.
- **HTTP method**: The action a request asks for, such as GET, POST, PUT or DELETE.
- **Safe method**: A method that shouldn't change anything on the server, such as GET.
- **Status code**: The three-digit number in a response saying how the request went.
- **HTTP header**: A named value in a request or response, such as Content-Type.
- **Message body**: The data after the headers of a request or response.
- **Chunked transfer encoding**: Sending a body in pieces, each with its own length, so the total needn't be known in advance.
- **Cookie**: A small value a server asks the browser to store and send back on later requests.
- **ETag**: An identifier for one version of a resource, used to check whether a cached copy is still current.
- **Conditional request**: A request that asks for a resource only if it has changed, answered with 304 when it hasn't.
- **CDN**: Content delivery network: caching servers in many cities that serve content close to users.
- **Persistent connection**: An HTTP connection kept open for further requests instead of being closed after one.
- **HTTP/2**: A binary version of HTTP that runs many requests at once over one connection.
- **QUIC**: A transport protocol on UDP with independent streams and a combined connection and TLS handshake.
- **HTTP/3**: HTTP carried over QUIC.
- **Reverse proxy**: A server that receives requests on behalf of other servers and forwards them.
- **Load balancer**: A reverse proxy that spreads requests across several servers and avoids unhealthy ones.

### In practice: realistic examples

2 worked scenarios of the kind you meet at work: the situation, what goes wrong, the code that fixes it, and the lesson.

#### Example 1: A GET link that deleted bookings

An email contains `GET /bookings/123/cancel`. A mail scanner prefetches links and cancels bookings.

*Use the right method*

```csharp
// GET must be safe: the link opens a confirmation page
app.MapGet("/bookings/{id}/cancel", (Guid id) => Results.Redirect($"/app/bookings/{id}/confirm-cancel"));

// the state change is a POST (or DELETE) from the page, with anti-forgery protection
app.MapPost("/bookings/{id}/cancellation", async (Guid id, CancelBooking handler, CancellationToken ct) =>
    await handler.HandleAsync(id, ct));
```

> **Lesson:** Crawlers, prefetchers and proxies assume GET is safe. Never change state with GET.

#### Example 2: A list endpoint that saves 200 KB per poll

A mobile app polls the flight-status list every 30 seconds, downloading the same 200 KB each time.

*ETag and 304*

```csharp
app.MapGet("/flights/status", async (HttpContext http, StatusStore store) =>
{
    var (version, data) = await store.GetAsync();
    var etag = $"\"{version}\"";
    if (http.Request.Headers.IfNoneMatch == etag) return Results.StatusCode(304);   // headers only
    http.Response.Headers.ETag = etag;
    http.Response.Headers.CacheControl = "private, max-age=0, must-revalidate";
    return Results.Ok(data);
});
```

> **Lesson:** Conditional requests turn repeated downloads into tiny 304 responses.

#### What HTTP actually is

This part is about designing APIs, and it assumes HTTP. The Networking part later covers the protocol properly; this is the minimum picture you need to make sense of everything before it.

##### A text request, and a text response

``` text
  a client opens a connection and sends TEXT. That is genuinely all it is.

  REQUEST
    POST /orders HTTP/1.1                <- METHOD, PATH, VERSION
    Host: api.example.com                <- HEADERS: metadata, one per line
    Content-Type: application/json
    Authorization: Bearer eyJhbGci...
    Content-Length: 41
                                         <- ONE BLANK LINE separates
    {"customerId":"acme","quantity":2}   <- BODY

  RESPONSE
    HTTP/1.1 201 Created                 <- VERSION, STATUS CODE, reason
    Content-Type: application/json       <- HEADERS
    Location: /orders/4471

    {"id":4471,"status":"Placed"}        <- BODY

  that is the entire protocol. Everything else - REST, OpenAPI, gRPC,
  GraphQL, webhooks - is a CONVENTION about what to put in those fields.
```

##### The parts, and what each is for

| Part             | Carries                         | Example                               |
|------------------|---------------------------------|---------------------------------------|
| **Method**       | What kind of operation this is  | `GET`, `POST`, `PUT`, `DELETE`        |
| **Path**         | Which resource                  | `/orders/4471`                        |
| **Query string** | Parameters that filter or shape | `?status=open&page=2`                 |
| **Headers**      | Metadata about the message      | Content type, authentication, caching |
| **Body**         | The payload                     | JSON, a form, a file                  |
| **Status code**  | What happened                   | `200`, `404`, `500`                   |

##### Stateless: the property everything else depends on

``` text
  HTTP is STATELESS. The server remembers NOTHING between requests.

    request 1: "log me in"        -> server: "here is a token"
    request 2: "give me /orders"  -> server: WHO ARE YOU?

  the server has no memory of request 1. So request 2 must carry proof
  of identity itself - a cookie, or an Authorization header.

  this one property is why:
    you can put a LOAD BALANCER in front and any instance can serve
      any request
    you can SCALE OUT by adding instances
    a RESPONSE CAN BE CACHED, because it depends only on the request
    "sticky sessions" are a workaround, and a smell
    every request re-sends its authentication

  the moment a server keeps per-user state in memory, it stops being
  freely replaceable - which is the whole argument in the scaling sections.
```

>
> **Why this matters for API design.** Because the server remembers nothing, *every request must be self-describing*: it carries who you are, what you want, and what format you expect. #### HTTP/1.1, HTTP/2, HTTP/3

|                  | HTTP/1.1                                     | HTTP/2                                | HTTP/3                                    |
|------------------|----------------------------------------------|---------------------------------------|-------------------------------------------|
| Transport        | TCP                                          | TCP                                   | QUIC over UDP                             |
| Concurrency      | One request per connection; browsers open ~6 | Multiplexed streams on one connection | Multiplexed, no TCP head-of-line blocking |
| Headers          | Plain text, repeated                         | HPACK compressed                      | QPACK compressed                          |
| Push / streaming | Chunked encoding                             | Bidirectional streams                 | Same, plus connection migration           |
| Requires TLS     | No                                           | In practice yes                       | Yes                                       |

HTTP/2 is the reason gRPC is efficient: one TCP connection carries hundreds of concurrent calls without queuing. But because it is one connection, a load balancer that balances per-connection will pin all your traffic to one backend pod — you need an L7 proxy that balances per-request.

``` csharp

{
    o.ListenAnyIP(8080, l => l.Protocols = HttpProtocols.Http1AndHttp2);
    o.Limits.MaxConcurrentConnections = 10_000;
    o.Limits.KeepAliveTimeout = TimeSpan.FromSeconds(120);
    o.Limits.MaxRequestBodySize = 30 * 1024 * 1024;
});
```

###### What actually changes for a .NET service

``` text
  HTTP/1.1   one request at a time per connection.
             browsers opened ~6 per origin to compensate.
             HttpClient opens up to MaxConnectionsPerServer.

  HTTP/2     ONE connection, many multiplexed streams.
             -> HttpClient uses a SINGLE connection for all concurrent
                requests to a host. This is usually good and occasionally
                a bottleneck: one TCP connection has one congestion window,
                so a slow link limits everything on it.
             -> and TCP head-of-line blocking: one lost packet stalls
                every stream on that connection.

  HTTP/3     over QUIC (UDP). Streams are independent at the TRANSPORT
             layer, so a lost packet stalls only its own stream.
             Faster handshake; connection migration across networks.

  the .NET-specific consequence of HTTP/2 multiplexing:
    MaxConnectionsPerServer stops being the concurrency limit.
    EnableMultipleHttp2Connections = true lets the handler open more
    than one when the stream limit is reached - worth setting for
    high-concurrency gRPC clients, which is where this bites.
```

``` csharp
// requesting a version, and what happens if the server disagrees
var client = new HttpClient(new SocketsHttpHandler
{
    EnableMultipleHttp2Connections = true,       // for high-concurrency gRPC
});
client.DefaultRequestVersion = HttpVersion.Version20;
client.DefaultVersionPolicy = HttpVersionPolicy.RequestVersionOrLower;
//   RequestVersionOrLower  - try 2, fall back to 1.1. The safe default.
//   RequestVersionExact    - fail if the server cannot do it
//   RequestVersionOrHigher - opportunistically upgrade

// Kestrel: which versions to accept
builder.WebHost.ConfigureKestrel(k =>
{
    k.ConfigureEndpointDefaults(o =>
        o.Protocols = HttpProtocols.Http1AndHttp2);   // gRPC needs Http2
});
// note: HTTP/2 requires TLS in every browser. Between your own services
// inside a network, h2c (cleartext HTTP/2) is normal - and it is what
// gRPC uses by default.
```

| Because of HTTP/2+ | Old advice                       | Now                                                      |
|--------------------|----------------------------------|----------------------------------------------------------|
| Multiplexing       | Concatenate files, sprite images | Ship separate files — better caching granularity         |
| Multiplexing       | Shard across subdomains          | **Harmful** — it forces extra connections and handshakes |
| Header compression | Minimise header count            | Much less important                                      |
| One connection     | Raise `MaxConnectionsPerServer`  | Consider `EnableMultipleHttp2Connections` instead        |

The practical note for a backend service: HTTP/2 to your *origin* matters less than expected, because a reverse proxy usually terminates it and speaks HTTP/1.1 upstream over a pooled keep-alive connection. Where it genuinely matters is **gRPC**, which requires it, and service-to-service calls where you control both ends.

### Ground Floor

<p class="src">From <em>Backend Engineering</em> · APIs · Ground Floor</p>

<a id="be-e494"></a>

#### Latency, and what it means for design

| Operation                  | Time    |
|----------------------------|---------|
| In-process method call     | ~1 ns   |
| Same-datacenter round trip | ~0.5 ms |
| Cross-region (US↔EU)       | ~80 ms  |
| Cross-planet               | ~250 ms |

**A network call is roughly a million times more expensive than a method call.** This single ratio drives most API design:

- Chatty APIs (ten calls to do one thing) are pathological. Batch instead.
- Round trips dominate payload size at small sizes. One 100 KB response usually beats ten 10 KB responses.
- The N+1 problem — fetch a list, then fetch details for each item — turns one operation into 101 round trips. It's the most common API performance bug.

<a id="be-e495"></a>

#### What can go wrong, and the fundamental ambiguity

A request can fail:

- Before leaving the client (DNS, no route)
- In transit (packet loss, connection reset)
- At the server, before processing (overload, rejected)
- At the server, **during** processing (crash halfway)
- At the server, **after** processing but before responding
- On the way back (response lost)

**The client cannot distinguish these.** A timeout tells you nothing about whether the work happened.

This is not a solvable problem — it's a theorem, not a bug. The Two Generals Problem proves no protocol can guarantee both sides agree on whether a message arrived. TCP acknowledgements move the uncertainty; they don't remove it.

Everything in Part IX — idempotency keys, safe retries, exactly-once semantics — is engineering *around* this permanent ambiguity, not eliminating it.

### HTTP

<p class="src">From <em>Backend Engineering</em> · APIs · HTTP</p>

<a id="be-e496"></a>

#### The shape of a message

HTTP is text (through 1.1) over a TCP byte stream. Every request:

``` yaml
POST /users?notify=true HTTP/1.1        ← request line
Host: api.example.com                   ┐
Content-Type: application/json          │
Content-Length: 27                      ├ headers
Authorization: Bearer eyJhbGci...       │
                                        ┘
                                        ← blank line: mandatory separator
{"name": "Nam", "age": 30}              ← body
```

Every response:

``` yaml
HTTP/1.1 201 Created                    ← status line
Content-Type: application/json          ┐ headers
Location: /users/42                     │
Content-Length: 31                      ┘

{"id": 42, "name": "Nam"}               ← body
```

Three parts, always: **what** (request/status line), **about it** (headers), **the data** (body).

That blank line is load-bearing. TCP gives you a stream of bytes with no message boundaries — nothing says "the message ends here." The blank line marks where headers stop, and `Content-Length` says how many body bytes follow. Get this wrong and you get **request smuggling**: two servers in a chain disagree about where one request ends, so an attacker can hide a second request inside the first.

This is also why credentials get Base64-encoded. Headers are delimited by newlines; a password containing `\r\n` would forge a header boundary. Base64's alphabet (`A–Z a–z 0–9 + / =`) contains no newlines, no control characters, no whitespace — so the value cannot escape its own field. Base64 is a *transport safety* measure, not a security one; it's reversible by anyone, instantly.

<a id="be-e497"></a>

#### Methods, and the two properties that matter

| Method    | Purpose        | Safe | Idempotent | Body |
|-----------|----------------|------|------------|------|
| `GET`     | retrieve       | ✅   | ✅         | no   |
| `HEAD`    | headers only   | ✅   | ✅         | no   |
| `OPTIONS` | capabilities   | ✅   | ✅         | no   |
| `POST`    | create / act   | ❌   | ❌         | yes  |
| `PUT`     | replace whole  | ❌   | ✅         | yes  |
| `PATCH`   | partial update | ❌   | ❌\*       | yes  |
| `DELETE`  | remove         | ❌   | ✅         | no   |

**Safe** = doesn't change state. Crawlers, prefetchers, and browsers assume this freely — a `GET` that deletes something *will* eventually be triggered by a link prefetcher.

**Idempotent** = doing it N times equals doing it once. This is the property that makes retries legal, so it's the most operationally important thing on the table. `PUT /users/42 {name:"Nam"}` twice leaves the same state. `POST /users` twice creates two users.

\* `PATCH` is idempotent only if the patch itself is (`{"status":"paid"}` is; `{"op":"increment"}` isn't).

`DELETE` is idempotent in *state* even though the second call returns 404 — the resource is gone either way. That's the correct reading.

<a id="be-e498"></a>

#### Status codes

The first digit is the whole message:

- **1xx** informational (rare; `101 Switching Protocols` for WebSockets)
- **2xx** it worked
- **3xx** look elsewhere
- **4xx** **you** made a mistake — don't retry unchanged
- **5xx** **I** made a mistake — retrying may work

That 4xx/5xx split is the contract with every client, proxy, and retry library in the world. Returning 500 for validation errors means clients retry something that can never succeed; returning 400 for a database outage means they give up on something transient.

The ones worth knowing precisely:

| Code                       | Meaning                                | Note                           |
|----------------------------|----------------------------------------|--------------------------------|
| 200 OK                     | success with body                      |                                |
| 201 Created                | resource created                       | include `Location` header      |
| 202 Accepted               | queued, not done                       | for async work                 |
| 204 No Content             | success, nothing to return             | typical for DELETE/PUT         |
| 301 / 308                  | moved permanently                      | 308 preserves the method       |
| 302 / 307                  | moved temporarily                      | 307 preserves the method       |
| 304 Not Modified           | your cache is valid                    | response has no body           |
| 400 Bad Request            | malformed / invalid                    |                                |
| **401 Unauthorized**       | **not authenticated**                  | misnamed; means "who are you?" |
| **403 Forbidden**          | **authenticated, not allowed**         | "I know you, no."              |
| 404 Not Found              | no such resource                       | also used to hide existence    |
| 405 Method Not Allowed     | wrong verb                             | must send `Allow` header       |
| 409 Conflict               | state conflict                         | duplicate, version mismatch    |
| 410 Gone                   | deliberately removed                   | permanent, unlike 404          |
| 412 Precondition Failed    | `If-Match` failed                      | optimistic concurrency         |
| 415 Unsupported Media Type | bad `Content-Type`                     |                                |
| 422 Unprocessable          | syntactically fine, semantically wrong | contested; 400 is fine too     |
| 429 Too Many Requests      | rate limited                           | must send `Retry-After`        |
| 500 Internal Server Error  | unhandled failure                      | never leak stack traces        |
| 502 Bad Gateway            | upstream returned garbage              |                                |
| 503 Service Unavailable    | temporarily down/overloaded            | send `Retry-After`             |
| 504 Gateway Timeout        | upstream too slow                      |                                |

401 vs 403 is the pair people get wrong most. 401 means *authenticate* (and the response must include a `WWW-Authenticate` header). 403 means *authentication succeeded and you still can't*.

<a id="be-e499"></a>

#### Headers worth knowing

**Request:**

``` yaml
Host: api.example.com               which site (many share an IP)
Authorization: Bearer <token>       who you are
Accept: application/json            what format you want back
Accept-Encoding: gzip, br           compression you support
Content-Type: application/json      what you're sending
Content-Length: 27                  how many body bytes
If-None-Match: "abc123"             conditional GET (caching)
If-Match: "abc123"                  optimistic concurrency
Idempotency-Key: <uuid>             safe-retry marker
X-Request-Id: <uuid>                tracing correlation
```

**Response:**

``` yaml
Content-Type: application/json      how to parse the body
Cache-Control: max-age=3600         caching rules
ETag: "abc123"                      version fingerprint
Location: /users/42                 where the new thing lives
Retry-After: 30                     when to try again
WWW-Authenticate: Bearer            how to authenticate
X-RateLimit-Remaining: 42           quota state
```

Custom headers conventionally used `X-` prefixes; RFC 6648 deprecated that in 2012, but the convention persists and is harmless.

<a id="be-e500"></a>

#### HTTP versions

|         | Transport           | Concurrency         | Headers      | Note                                  |
|---------|---------------------|---------------------|--------------|---------------------------------------|
| **1.0** | new TCP per request | none                | text         | handshake per request                 |
| **1.1** | keep-alive          | pipelining (broken) | text         | still the default mental model        |
| **2**   | one TCP             | true multiplexing   | HPACK binary | head-of-line blocking at TCP layer    |
| **3**   | QUIC over UDP       | multiplexing        | QPACK        | no TCP HOL blocking; faster handshake |

HTTP/1.1's limitation: one request at a time per connection. Browsers work around it with ~6 parallel connections per host. HTTP/2 multiplexes many streams over one connection, which removes that limit — and makes domain sharding an anti-pattern.

Semantics are identical across versions. Methods, status codes, and headers mean the same thing; only the wire encoding changes. Your API code shouldn't care, but your gRPC service requires HTTP/2, and some corporate proxies still don't speak it.

### One Call, End to End

<p class="src">From <em>Backend Engineering</em> · APIs · One Call, End to End</p>

<a id="be-e502"></a>

#### One Call, End to End

Everything in Part 0 and I, as a single timeline. A client calls `GET https://api.example.com/users/42`. Times are illustrative; the ordering is real.

**t = 0 ms — DNS.** The client needs an IP. Check the OS cache; on a miss, ask the resolver, which may walk root → `.com` → `example.com`'s nameservers. **20–100 ms on a cold cache, ~0 ms warm.** Note that nothing HTTP has happened yet.

**t = 30 ms — TCP handshake.** SYN → SYN-ACK → ACK. One round trip, so ~50 ms on a 50 ms link. A source port is allocated from the ephemeral range; this is the port that `TIME_WAIT` will hold for minutes after close.

**t = 80 ms — TLS handshake.** Client hello (with SNI — the hostname, in the clear), server certificate, key exchange. **TLS 1.3: one round trip. TLS 1.2: two.** The client validates the certificate chain to a trusted CA and checks the hostname matches.

**t = 130 ms — the request finally goes out.** ~200 bytes of text:

``` yaml
GET /users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGci...
Accept: application/json
Accept-Encoding: gzip, br
```

Everything before this point — 130 ms — was setup. **This is why connection reuse dominates every other client-side optimization.** The second request on this connection starts here, at t=0.

**t = 155 ms — arrival at the edge.** The packet reaches a load balancer or CDN. It reads the *headers only* to route — never the body. This is what the uniform interface buys you: intermediaries can act without understanding your domain. TLS often terminates here, and a fresh connection continues inward.

**t = 157 ms — gateway.** Rate limit checked against a counter (usually Redis). If exceeded: `429` with `Retry-After`, and the request never reaches your service. Token validated — signature, `exp`, `iss`, `aud`. If the JWT is bad: `401`, again without touching your code.

**t = 160 ms — your service.** Kestrel accepts the connection, parses the request line and headers, routes on method + path, and binds `42` to your parameter. `HttpContext.RequestAborted` is now live — if the client hangs up, this token fires.

**t = 161 ms — authorization.** Authentication already happened at the gateway; **this is the different question.** Is *this* subject allowed *this* resource? The token says who you are; it doesn't say user 42's record is yours to read. Skipping this line is BOLA, OWASP API \#1.

**t = 162 ms — the database call.** Connection from the pool (or a wait if exhausted), query issued, ~5 ms. This is where the async reference takes over: the thread is released at the await and the request exists only as a heap object until the reply lands.

**t = 168 ms — serialization.** The domain object becomes JSON. Naming policy, null handling, date format, and — critically — whether the ID goes out as a number or a string all apply here. A 64-bit ID as a JSON number silently corrupts in any JavaScript client.

**t = 169 ms — the response.**

``` yaml
HTTP/1.1 200 OK
Content-Type: application/json
ETag: "v3-abc123"
Cache-Control: private, max-age=60
Content-Encoding: gzip
```

`ETag` and `Cache-Control` are set here and cost nothing. They're what make the *next* request free.

**t = 200 ms — client receives.** Decompress, deserialize, done.

**Total: ~200 ms, of which ~130 ms was connection setup and ~7 ms was actual work.**

Now the second request, one second later, same client:

**t = 0 ms.** Connection already open — no DNS, no TCP, no TLS. The client sends `If-None-Match: "v3-abc123"`.

**t = 25 ms.** Server compares the ETag, nothing changed, returns `304 Not Modified` with **no body**.

**Total: 25 ms and ~150 bytes**, versus 200 ms and a full payload.

That's an 8× improvement from two response headers and one request header. It's the highest ratio of benefit to effort anywhere in API design, and it's the thing most APIs skip entirely.

**Now the failure case.** Same request, but the database is slow and the gateway times out at 30 seconds while your service is still working.

The client gets `504`. But: **your service completes the query at 35 seconds and commits.** If this had been a `POST /payments`, the client saw a failure and the payment happened. The client retries. Without an idempotency key, the customer is charged twice.

This is Fact 2 from the top of the document, made concrete. The timeout told the client nothing about whether the work occurred. No amount of protocol design fixes that — only idempotency keys make the retry safe.

#### HTTP semantics: methods, status and headers

| Method    | Safe | Idempotent | Meaning                                                                  |
|-----------|------|------------|--------------------------------------------------------------------------|
| `GET`     | Yes  | Yes        | Retrieve. Must not change state — crawlers and prefetchers will call it  |
| `HEAD`    | Yes  | Yes        | Headers only. Useful for existence and size checks                       |
| `POST`    | No   | **No**     | Create, or anything not covered by the others. Not safe to retry blindly |
| `PUT`     | No   | Yes        | Replace the whole resource at a known URL                                |
| `PATCH`   | No   | No         | Partial update                                                           |
| `DELETE`  | No   | Yes        | Remove. Deleting twice leaves it deleted                                 |
| `OPTIONS` | Yes  | Yes        | Capabilities. What a CORS preflight uses                                 |

**Safe** means no side effects. **Idempotent** means doing it repeatedly has the same effect as doing it once. These are not academic: proxies, browsers and retry policies all rely on them, and a `GET` that mutates state will eventually be triggered by a link prefetcher.

| Status                      | Means                                                       | Commonly misused as                                                            |
|-----------------------------|-------------------------------------------------------------|--------------------------------------------------------------------------------|
| **200**                     | OK                                                          | Returned alongside an error in the body — breaks every client's error handling |
| **201**                     | Created — include a `Location` header                       |                                                                                |
| **202**                     | Accepted, processing asynchronously                         | The right answer for a queued job                                              |
| **204**                     | Success, no body                                            |                                                                                |
| **301** / **308**           | Permanent redirect — **cached aggressively, often forever** | Use 302/307 unless you are certain                                             |
| **304**                     | Not modified — use your cached copy                         |                                                                                |
| **400**                     | Malformed request                                           | Used for business-rule failures, which should be 409 or 422                    |
| **401**                     | Not authenticated — *who are you?*                          | Confused with 403 constantly                                                   |
| **403**                     | Authenticated but not permitted                             |                                                                                |
| **404**                     | Not found                                                   | Also correct for ‘exists but you may not know that’                            |
| **409**                     | Conflict with current state                                 | The right code for an optimistic-concurrency failure                           |
| **422**                     | Well-formed but semantically invalid                        |                                                                                |
| **429**                     | Rate limited — include `Retry-After`                        |                                                                                |
| **500**                     | We broke                                                    | Should never carry a stack trace to the client                                 |
| **502** / **503** / **504** | Upstream broken / unavailable / timed out                   | Emitted by proxies, not usually by your app                                    |

> **\[Trap\]**
>
> **Common trap.** A `301` is cached by browsers essentially permanently and is very difficult to undo — users who received it will not ask you again. Deploy a redirect as `302`, confirm it is correct in production, and only then consider making it permanent.

<a id="be-g641"></a>

#### HTTP/1.1, HTTP/2 and HTTP/3

``` text
  HTTP/1.1     one request at a time per connection
               browsers opened ~6 connections per origin to compensate
               -> hence sprite sheets, domain sharding, file concatenation

  HTTP/2       ONE connection, many multiplexed streams, binary framing,
               header compression (HPACK), server push (now deprecated)
               -> those 1.1 workarounds became counterproductive
               -> still suffers TCP head-of-line blocking: one lost packet
                  stalls every stream

  HTTP/3       HTTP/2 semantics over QUIC (UDP)
               -> independent streams: a lost packet stalls only its stream
               -> faster handshake, connection migration across networks
```

| Because of HTTP/2+ | Old advice                     | Now                                                  |
|--------------------|--------------------------------|------------------------------------------------------|
| Multiplexing       | Concatenate files, use sprites | Ship separate files — better caching granularity     |
| Multiplexing       | Shard across subdomains        | Harmful — it forces extra connections and handshakes |
| Header compression | Minimise header count          | Much less important                                  |
| One connection     | Six parallel connections       | One, with many streams                               |

``` bash
curl -sI --http2 https://example.com | head -1     # HTTP/2 200
curl -sI --http3 https://example.com | head -1     # HTTP/3 200

# HTTP/2 requires TLS in every browser. There is no practical h2c on the public web.
# Between your own services inside a network, h2c (cleartext HTTP/2) is common
# and is what gRPC uses.
```

One operational note: HTTP/2 to your *origin* matters less than you would think, because a reverse proxy usually terminates it and speaks HTTP/1.1 upstream over a pooled keep-alive connection. The multiplexing benefit is mostly between the browser and the edge.

> **\[Why it matters\]** Protocol version silently decides real behaviour — whether one slow response blocks others, whether gRPC works at all, whether a proxy in the path downgrades you without saying so. It is also the first thing to check when the same application performs differently in two environments.
