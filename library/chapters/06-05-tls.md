# 6.5 TLS

> **Quick look.** TLS gives connections confidentiality, integrity and proof of the server's identity.
>
> - A short asymmetric handshake agrees a key and proves identity; fast symmetric encryption carries the data.
> - A certificate binds a public key to a domain name, signed up a chain to a trusted root.
> - TLS 1.3 needs one round trip and always gives forward secrecy.
> - It hides content, not the fact that you connected; SNI reveals the host name.
> - Automate renewal and monitor expiry from outside: expired certificates cause many avoidable outages.
> - Never disable certificate validation, even in staging; mTLS adds client identity.


### The big picture

A packet on its way to a server passes through many machines you don't control: the café's Wi-Fi, your ISP, several routers, perhaps a corporate proxy. Without protection, any of them could read the packet, such as a password, a card number or a passport scan, or quietly change it. Worse, you couldn't even be sure the machine answering is the real server rather than an impostor.

TLS, Transport Layer Security, solves all three problems. It is the "S" in HTTPS and the padlock in the browser. Think of it as a sealed, tamper-evident envelope combined with an identity check: before anything is sent, the server proves who it is with a certificate vouched for by a trusted third party. This chapter explains the ideas underneath, in plain terms: encryption with one key and with two, certificates and who signs them, and the handshake that sets it all up. It then covers what TLS doesn't hide, and the mistakes that quietly turn it off.

**1. What three protections does TLS provide?**

> Confidentiality: others on the path can't read the data. Integrity: they can't change it without being detected. Authentication: the client knows it is talking to the real owner of the name it asked for.

**2. Why does TLS use both asymmetric and symmetric encryption?**

> Asymmetric cryptography lets two strangers agree on a secret key and lets the server prove its identity, but it is slow. Symmetric encryption with the agreed key is fast, so it protects the actual data.

**3. What does a certificate prove, and who vouches for it?**

> That a public key belongs to the owner of a domain name. A certificate authority checks control of the domain and signs the certificate. Clients trust it because the signature chains up to a root certificate they already trust.

**4. Why is a certificate validation callback that always returns true so dangerous?**

> It turns off authentication. Any machine on the path can then present its own certificate, read everything and pass it on. The connection is still encrypted, but to the attacker.

**5. What is SNI, and what does it reveal?**

> Server Name Indication: the client sends the name of the site it wants at the very start of the handshake, so a server hosting many sites can pick the right certificate. That name is visible to anyone watching, unless Encrypted Client Hello is used.

**6. How many round trips does a TLS 1.3 handshake take?**

> One, on top of the TCP handshake. Resumed connections can even send data in the first flight, called 0-RTT, with some limits because that data can be replayed.

**7. What happens the moment a server's certificate expires?**

> Every client that checks it refuses to connect. Expired certificates are one of the most common causes of complete outages. Renew automatically and monitor expiry dates.

### The problem

Layers and packets (6.1) showed that packets travel through many machines on their way. Every one of them can read what passes through. On an unencrypted connection, the data is **plaintext**: readable exactly as sent.

Three separate things are at risk. Someone could read the data: that is a failure of confidentiality. Someone could change it, for example to alter an account number: a failure of integrity. And someone could pretend to be the server: a failure of authentication. An attacker who sits between the two ends, reading and relaying traffic while each side thinks it is talking directly to the other, is making a **man-in-the-middle attack**.

**TLS**, Transport Layer Security, protects against all three. It runs on top of TCP and below the application protocol, so HTTP, database protocols, email and many others can all use it without changing. HTTP over TLS is **HTTPS**, on port 443. TLS replaced an older protocol called SSL, and people still say "SSL certificates", although every version of SSL is long broken.

### Encryption with one key

**Encryption** turns plaintext into **ciphertext**, which looks like random bytes to anyone without the key, and decryption turns it back. The key is a secret value, typically 128 or 256 bits long. The algorithms themselves are public; all of the secrecy is in the key.

In **symmetric encryption**, the same key encrypts and decrypts. The standard algorithm is AES, the Advanced Encryption Standard. Modern processors have instructions just for it, and it encrypts gigabytes per second. TLS also uses modes of encryption that attach a short authentication tag to each piece of data, so any change to the ciphertext is detected. That gives integrity as well as confidentiality.

Symmetric encryption has one big problem: both sides need the same secret key. Two machines meeting for the first time, over a network anyone can watch, can't simply send the key across.

### Encryption with two keys

**Asymmetric encryption**, also called public-key cryptography, solves that. Each party has a **key pair**: a public key, which can be given to anyone, and a private key, which is kept secret. The two are mathematically linked, but the private key can't feasibly be worked out from the public one.

Key pairs enable two things TLS needs.

A **key exchange** lets two parties agree on a shared secret over an open network. Each side makes a temporary key pair and sends the public half. Each side combines its own private half with the other's public half, and both end up with the same secret number, which nobody watching can compute. This is the Diffie-Hellman method, published in 1976. TLS uses a modern elliptic-curve version. The shared secret becomes the symmetric key for the connection.

A **digital signature** proves who created some data and that it hasn't changed. The signer computes a signature from the data with their private key. Anyone with the public key can check it. A valid signature means the holder of that private key signed exactly this data.

Asymmetric operations are much slower than symmetric ones, so TLS uses them only during setup. Everything afterwards uses fast symmetric encryption with the agreed key.

Because the key-exchange key pairs are temporary and thrown away after each connection, recording today's encrypted traffic and stealing the server's long-term private key next year still doesn't let anyone decrypt it. That property is called **forward secrecy**, and TLS 1.3 always provides it.

### Certificates

A key exchange alone doesn't stop an impostor. An attacker in the middle could run a perfectly good key exchange with each side. The client needs to know that the public key it received really belongs to `example.com`.

A **certificate** makes that link. It is a small document that contains a public key, the domain names it is valid for, a validity period and a few other details, all digitally signed by a **certificate authority** (CA). Before signing, the CA checks that whoever asked for the certificate really controls the domain, for example by asking them to publish a specific DNS record or file.

A client checks four things. The name it asked for matches a name in the certificate. The current date is within the validity period. The signature is valid. And the signer is trusted. Signers are usually intermediate CAs, whose own certificates are signed by root CAs. The chain from the server's certificate up through intermediates to a root is the **certificate chain**. Each operating system and browser ships a **trust store**: the list of root certificates it trusts. A certificate is accepted only if its chain ends at one of them.

Certificates expire deliberately, so that a stolen private key is only useful for a limited time. Lifetimes keep getting shorter. Browser makers and CAs have agreed limits that fell to 200 days in March 2026 and fall to 47 days by 2029. At those lifetimes, renewal has to be automated. The ACME protocol, created by the free certificate authority Let's Encrypt, does it: a small client proves domain control and fetches a fresh certificate on a schedule. Cloud providers renew certificates for their load balancers automatically.

### The handshake

Before any application data flows, client and server run the TLS handshake. In TLS 1.3, the current version, it takes one round trip.

The client sends a ClientHello. It lists the encryption methods it supports, includes its half of a key exchange and names the site it wants, using **SNI**, Server Name Indication. SNI matters because one server address often hosts many sites, and the server needs to know which certificate to present.

The server replies with a ServerHello: its half of the key exchange, its chosen method, its certificate chain, a signature proving it holds the private key for that certificate, and a message confirming the handshake so far wasn't tampered with. From this point, everything is encrypted.

The client checks the certificate and the signature, finishes the key exchange and sends its own confirmation. Application data now flows, protected by the symmetric keys both sides derived.

A client returning to a server it spoke to recently can resume a session and even send data in its first message, called 0-RTT. That early data can be replayed by an attacker, so servers should only accept it for requests that are safe to repeat, the idempotent ones from Errors and exceptions (2.8).

### Seeing it for real

This program opens a TLS connection by hand and prints what was agreed. It also tries a test site whose certificate has deliberately expired.

```csharp
// tls.cs — run with: dotnet run tls.cs   (needs an internet connection)
using System.Net.Security;
using System.Net.Sockets;
using System.Security.Authentication;
using System.Security.Cryptography.X509Certificates;

foreach (string host in new[] { "example.com", "expired.badssl.com" })
{
    try
    {
        using var tcp = new TcpClient();
        await tcp.ConnectAsync(host, 443);                       // an ordinary TCP connection first
        using var tls = new SslStream(tcp.GetStream());
        await tls.AuthenticateAsClientAsync(host);               // the handshake, including the certificate checks for this name
        var cert = (X509Certificate2)tls.RemoteCertificate!;     // .NET hands back an X509Certificate2
        Console.WriteLine($"{host}: {tls.SslProtocol}, {tls.NegotiatedCipherSuite}");
        Console.WriteLine($"  certificate for {cert.GetNameInfo(X509NameType.DnsName, false)}");
        Console.WriteLine($"  signed by {cert.GetNameInfo(X509NameType.SimpleName, true)}");
        Console.WriteLine($"  valid until {cert.NotAfter:yyyy-MM-dd}, {(cert.NotAfter - DateTime.Now).Days} days from now");
    }
    catch (AuthenticationException ex) { Console.WriteLine($"{host}: refused: {ex.Message}"); }
    catch (SocketException ex) { Console.WriteLine($"{host}: could not connect: {ex.SocketErrorCode}"); }
}
// example.com: Tls13, TLS_AES_256_GCM_SHA384   (the exact method can vary)
//   certificate for example.com (or a name covering it)
//   signed by an intermediate certificate authority
//   valid until a date a few months away
// expired.badssl.com: refused: The remote certificate is invalid ...
```

Notice what the code doesn't do: it never switches the checks off. That second host is refused, and that is the correct outcome.

### What TLS doesn't hide

TLS protects the content of the conversation. It doesn't hide that the conversation happened.

Anyone on the path still sees both IP addresses, when the connection happened, how long it lasted and roughly how much data went each way. The SNI name in the ClientHello is sent unencrypted, so the name of the site is visible too, unless both sides support Encrypted Client Hello, which is still being rolled out. DNS lookups before the connection reveal the name as well, unless they are encrypted, as DNS (6.4) explained.

TLS also protects only the connection. Once data arrives at the server, it is ordinary data in memory, logs and databases, and protecting it there is a separate job, covered in Secrets and cryptography basics (10.5).

### TLS in .NET

Most of the time, TLS is invisible in .NET code. `HttpClient` negotiates it for any `https://` address, checks the certificate against the operating system's trust store and fails with an exception if anything is wrong. ASP.NET Core's server, Kestrel, serves HTTPS with a certificate you configure. For local development, `dotnet dev-certs https --trust` creates a certificate your own machine trusts.

Leave the protocol version to the operating system. Modern systems use TLS 1.3 or 1.2 and refuse the old, broken versions. TLS 1.0 and 1.1 were formally retired in 2021. Hard-coding one version in code means your app can't benefit when the OS moves on.

The one setting to be wary of is the certificate validation callback: `ServerCertificateCustomValidationCallback` on `HttpClientHandler`, or `RemoteCertificateValidationCallback` on `SslStream`. Code copied from forums often sets it to return `true` "to fix a certificate error". That turns off authentication entirely, and anyone on the path can intercept the connection. If a certificate fails validation, fix the certificate or trust the right private CA. Never accept everything.

### Where TLS ends

Many systems don't run TLS all the way to the application. A load balancer or reverse proxy in front of the servers holds the certificate, decrypts the traffic and passes it on, often as plain HTTP inside the private network. This is **TLS termination**. It centralizes certificate management and lets the load balancer inspect requests. The trade-off is that traffic behind it is unencrypted unless you re-encrypt it, and many organizations now require encryption inside their networks too.

Usually only the server proves its identity, while the client proves its own later, with a password or token. In **mutual TLS** (mTLS), the client also presents a certificate, and the server checks it. Service meshes and banking or government systems use mTLS so that services can only talk to other services with valid certificates.

A web server can also tell browsers to always use HTTPS for its site, even if a user types `http://`. That is **HSTS**, HTTP Strict Transport Security: a response header the browser remembers for a set period. It closes the gap in which an attacker could intercept the first unencrypted request.

### In short

TLS gives connections confidentiality, integrity and authentication. It uses asymmetric cryptography during a short handshake to agree a secret key and prove the server's identity, then fast symmetric encryption for the data. A certificate links a public key to a domain name, signed by a certificate authority whose chain ends at a trusted root. TLS 1.3 needs one round trip and always gives forward secrecy. It hides content, not the fact that you connected. Renew certificates automatically, and never disable certificate validation.

### What goes wrong

**Disabling certificate validation.** A callback that returns `true` makes every connection open to interception. Fix the certificate or trust the correct CA instead.

**Expired certificates.** Everything that depends on a service fails at once on the expiry date. Automate renewal with ACME or managed certificates, and alert well before expiry.

**Missing intermediate certificates.** A server that sends only its own certificate works in browsers that cache intermediates and fails in other clients. Configure the full chain.

**Name mismatches.** Connecting by IP address, or by an internal name the certificate doesn't list, fails validation. Connect by a name the certificate covers.

**Private keys in source control.** A committed key lets anyone impersonate the service. Keep keys in a secret store or let the platform manage them, as Secrets and cryptography basics (10.5) explains.

**Unencrypted traffic behind termination.** Traffic from the load balancer to servers crosses the internal network in plaintext. Re-encrypt it where policy or risk requires.

**Pinning old protocol versions.** Code that forces an old TLS version breaks when servers drop it and misses newer, safer ones. Let the OS choose.

### Cost model

A TLS 1.3 handshake costs one extra round trip and a few milliseconds of processor time for the key exchange and signature checks. Once connected, AES encryption with hardware support runs at gigabytes per second per core, so it adds very little to each request. The handshake is the real cost, which is one more reason connection pools matter: a reused connection pays it once. Session resumption shortens later handshakes to the same server.

### In other languages (optional)

**JavaScript and TypeScript.** Browsers handle TLS completely and show certificate errors to the user; pages can't override them. In Node.js, `https` and `tls` modules do the same. Setting `NODE_TLS_REJECT_UNAUTHORIZED=0` disables validation for the whole process and should never reach production.

**Python.** The `ssl` module and libraries like `requests` validate certificates by default. `verify=False` in `requests` is the same trap as a validation callback that returns true.

**Command line.** `openssl s_client -connect example.com:443 -servername example.com` shows the handshake, the certificate chain and the negotiated method.

### Key terms

- **Plaintext**: Data in its readable, unencrypted form.
- **Ciphertext**: Encrypted data, unreadable without the key.
- **Man-in-the-middle attack**: An attacker secretly relaying, reading or changing traffic between two parties.
- **TLS**: Transport Layer Security: the protocol that encrypts and authenticates connections.
- **HTTPS**: HTTP carried over TLS, normally on port 443.
- **Encryption**: Turning plaintext into ciphertext using a key, so only key holders can read it.
- **Symmetric encryption**: Encryption where the same key encrypts and decrypts, such as AES.
- **Asymmetric encryption**: Encryption using a key pair: a public key anyone may have and a private key kept secret.
- **Key pair**: A public key and its matching private key.
- **Key exchange**: A method for two parties to agree on a shared secret key over an open network.
- **Digital signature**: A value made with a private key that proves who signed some data and that it hasn't changed.
- **Forward secrecy**: The property that stealing a long-term key later doesn't reveal past recorded traffic.
- **Certificate**: A signed document linking a public key to one or more domain names.
- **Certificate authority**: An organization that verifies domain control and signs certificates. Often shortened to CA.
- **Certificate chain**: The sequence of certificates from a server's certificate up to a trusted root.
- **Trust store**: The set of root certificates an operating system or browser trusts.
- **SNI**: Server Name Indication: the site name a client sends at the start of the handshake.
- **TLS termination**: Decrypting TLS at a load balancer or proxy in front of the real servers.
- **Mutual TLS**: TLS where the client also proves its identity with a certificate. Often shortened to mTLS.
- **HSTS**: HTTP Strict Transport Security: a header telling browsers to always use HTTPS for a site.

### In practice: realistic examples

2 worked scenarios of the kind you meet at work: the situation, what goes wrong, the code that fixes it, and the lesson.

#### Example 1: The certificate that expired on a Sunday

Every client fails with a TLS error at 02:00 Sunday. Renewal had been failing silently for weeks.

*Monitor expiry from outside*

```bash
# days until expiry, run from a separate monitoring host
echo | openssl s_client -connect book.example.com:443 -servername book.example.com 2>/dev/null \
  | openssl x509 -noout -enddate
# alert at 21 days, page at 7 days; automate renewal with ACME (e.g. cert-manager, Let's Encrypt)
```

> **Lesson:** Automate renewal, and monitor expiry from somewhere other than the system doing the renewing.

#### Example 2: "Just disable validation in staging"

A developer adds a handler that accepts any certificate to get past a staging error. It ships to production in a shared library.

*Never do this*

```csharp
// ServerCertificateCustomValidationCallback = (_, _, _, _) => true;   // accepts any impostor
```

*Trust the right CA instead*

```bash
# add the staging CA to the container's trust store
COPY staging-ca.crt /usr/local/share/ca-certificates/
RUN update-ca-certificates
```

> **Lesson:** Disabling validation removes the identity check that TLS exists for. Fix trust, not the check.

#### HTTPS, briefly

TLS gives you three things:

- **Confidentiality** — nobody can read it
- **Integrity** — nobody can alter it undetected
- **Authentication** — the server is who it claims (via certificates and a chain of trust to a CA)

What it doesn't give you: authentication of the *client* (unless you use mTLS), and any protection once the message is decrypted at the far end.

Note what's *not* encrypted: the destination IP, and — unless Encrypted Client Hello is in play — the hostname in the TLS SNI field. An observer knows you talked to `api.example.com`, just not what you said.

**mTLS** adds a client certificate, so both sides authenticate. Standard for service-to-service in zero-trust networks; heavy for public APIs because certificate distribution and rotation is real work.

#### TLS, certificates and mTLS

TLS gives you three things: encryption, integrity, and authentication of the server. Certificates are how the third one works — a chain of signatures from your server's cert up to a root your client already trusts.

``` text
  TLS 1.3 handshake (1 round trip)

  client  --- ClientHello: versions, cipher suites, key share, SNI --->  server
  client  <-- ServerHello + certificate chain + Finished           ---   server
  client  --- Finished, then encrypted application data            --->  server

  the client verifies: chain trusted? not expired? hostname matches SAN? not revoked?
```

| Failure                         | Actual cause                                                             |
|---------------------------------|--------------------------------------------------------------------------|
| `RemoteCertificateNameMismatch` | Connecting by IP or an alias not in the SAN list                         |
| `RemoteCertificateChainErrors`  | Intermediate certificate not served, or an untrusted internal CA         |
| `UntrustedRoot` in a container  | The base image has no CA bundle, or your corporate root is not installed |
| Works locally, fails in prod    | Dev-only `ServerCertificateCustomValidationCallback` returning true      |

##### Mutual TLS

With mTLS the *client* also presents a certificate, so the server authenticates the caller with no tokens involved. It is the standard for service-to-service auth inside a mesh, and for bank and government integrations.

``` csharp
var handler = new SocketsHttpHandler();
handler.SslOptions.ClientCertificates =
    [X509CertificateLoader.LoadPkcs12FromFile("client.pfx", pwd)];
using var http = new HttpClient(handler);
```

> **\[Trap\]**
>
> **Common trap.** Certificate expiry is a scheduled outage you agreed to in advance. Automate renewal (ACME, cert-manager, Key Vault rotation) and alert at 30 days, not on the day.

###### What this looks like when it breaks

The four TLS failures you will actually meet, with the command that diagnoses each in under a minute.

| Error                                      | Real cause                                                                                                                     | Diagnose with                                                                               |
|--------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| `RemoteCertificateNameMismatch`            | Connecting by IP, or a hostname not in the SAN list. Note that CN is ignored by modern clients — only SAN counts               | `openssl s_client -connect h:443 -servername h` then read `X509v3 Subject Alternative Name` |
| `PartialChain` / `UntrustedRoot`           | The server is not sending its intermediate certificate. Browsers often paper over this by caching intermediates; .NET does not | `openssl s_client` — count the certificates in the chain it returns                         |
| Works on the host, fails in the container  | The slim base image has no CA bundle, or the corporate root CA is not installed                                                | `ls /etc/ssl/certs | wc -l` inside the container                                            |
| `The handshake failed... protocol version` | One side disabled TLS 1.0/1.1 and the other requires it; or a cipher-suite mismatch after an OS hardening policy               | `openssl s_client -tls1_2` vs `-tls1_3`                                                     |

``` text
# the one command that answers most of it
openssl s_client -connect api.internal:443 -servername api.internal -showcerts </dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# in a container, install the corporate root properly
COPY corporate-root.crt /usr/local/share/ca-certificates/
RUN update-ca-certificates
```

> **\[Trap\]**
>
> **Common trap.** The ‘fix’ you will find on Stack Overflow is `ServerCertificateCustomValidationCallback = (_,_,_,_) => true`. That disables certificate validation entirely, which means TLS provides encryption but no authentication — any machine-in-the-middle can impersonate the server and you will never know. If it must exist for local development, wrap it in `#if DEBUG` and an environment check, and add a test that fails if it is ever reachable in Release.

###### Certificate rotation without downtime

1.  **Automate issuance.** cert-manager in Kubernetes, ACME/Let's Encrypt at the edge, or Key Vault with auto-rotation. Manual renewal is a scheduled outage that has not happened yet.
2.  **Reload without restarting.** Kestrel supports a certificate selector callback, so a rotated file is picked up on the next handshake.
3.  **Overlap validity.** Issue the new certificate before the old one expires and serve both during the window; clients pinning the old one still work.
4.  **Alert at 30 and 7 days.** On the certificate the service is actually serving, not the one in the vault — those diverge more often than you would think.
5.  **Include client certificates and signing keys.** mTLS client certs, JWT signing keys and code-signing certificates all expire too, and are forgotten far more often than the public TLS cert.

``` csharp
builder.WebHost.ConfigureKestrel(o =>
{
    o.ConfigureHttpsDefaults(https =>
    {
        https.ServerCertificateSelector = (_, _) => _certStore.Current;   // re-read on rotation
    });
});

// a file watcher swaps _certStore.Current when the mounted secret changes
```

#### TLS: what the handshake establishes

TLS wraps a TCP connection to provide three distinct things — and it is worth separating them, because people conflate them constantly.

| Property            | Means                          | Without it                           |
|---------------------|--------------------------------|--------------------------------------|
| **Confidentiality** | nobody in between can read it  | any hop sees your credentials        |
| **Integrity**       | nobody can alter it undetected | content can be silently modified     |
| **Authentication**  | the server is who it claims    | you may be encrypting to an attacker |

``` text
TLS 1.3 handshake - one round trip on top of TCP's:

  client ─── ClientHello: versions, ciphers, key share, SNI, ALPN ───►
  client ◄── ServerHello + certificate + Finished ────────────────────
  client ─── Finished ───────────────────────────────────────────────►
  encrypted application data flows.

  TCP handshake  1 RTT
  TLS handshake  1 RTT      -> 2 RTTs before your first byte.
  Cross-region at 80 ms RTT, that is 160 ms of pure setup.
  Session resumption reduces a reconnect to 0-1 RTT.
```

**Authentication rests on the certificate chain.** The server presents a certificate signed by an intermediate, signed by a root your machine already trusts. Your client verifies the signatures, the expiry, and that the name matches what you asked for. Disabling that check — the infamous "accept any certificate" workaround — discards *all three* properties, because an attacker who can intercept can now also present their own certificate.

> **\[Trap\]** **Never do this, including in staging:**
>
> ``` csharp
> handler.ServerCertificateCustomValidationCallback = (_, _, _, _) => true;
> ```
>
> It reliably survives into production, because it makes the error go away and nothing later fails. If a certificate does not validate, fix the certificate or add the internal CA to the trust store — both take minutes and neither leaves a permanent hole ([Handling sensitive data](10-06-privacy-compliance-and-the-supply-chain.md#be-m227)).

> **\[Tip\]**
>
> **ALPN in the ClientHello is how HTTP/2 gets negotiated** — the client lists protocols it speaks and the server picks. This is why HTTP/2 in practice requires TLS even though the specification does not, and why an intercepting proxy can silently downgrade you to HTTP/1.1 ([HTTP/1.1, HTTP/2, and HTTP/3](06-06-http.md#be-a159)).

#### TLS: the handshake and the chain

``` text
  TLS 1.3 handshake - one round trip

  client ---- ClientHello ----------------------> server
              supported ciphers, key share, SNI
         <--- ServerHello, certificate, Finished
              chosen cipher, key share, cert chain
         ---- Finished + application data ------->

  what it gives you
    CONFIDENTIALITY   nobody on the path can read it
    INTEGRITY         nobody can modify it undetected
    AUTHENTICATION    the server is who the certificate says
                      (mTLS adds: and so is the client)

  what it does NOT give you
    authorisation, input validation, or protection from a compromised endpoint
```

``` text
  the certificate chain - what "trusted" means

  ROOT CA            self-signed, pre-installed in the OS/browser trust store
    | signs
  INTERMEDIATE CA    what actually signs your cert; kept offline-ish
    | signs
  LEAF               your certificate: api.example.com, valid 90 days

  the server must send LEAF + INTERMEDIATE(S). It must NOT send the root.
  the single most common TLS misconfiguration is omitting the intermediate:
  browsers often paper over it by fetching the missing link,
  but curl, Java clients and mobile apps FAIL. So it "works in my browser"
  and breaks every API client.
```

``` text
# inspect what a server actually presents
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null

# the chain it sends, and whether it verifies
openssl s_client -connect api.example.com:443 -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# expiry, quickly
echo | openssl s_client -connect api.example.com:443 2>/dev/null \
  | openssl x509 -noout -enddate

# SNI matters: one IP serves many certificates, selected by the name the
# client sends. Omit -servername and you may get the wrong certificate.
```

| TLS error                                | Meaning                                                               |
|------------------------------------------|-----------------------------------------------------------------------|
| `certificate has expired`                | Renewal failed. Alert on this at 30, 14 and 7 days                    |
| `unable to get local issuer certificate` | Missing intermediate, or the client's trust store lacks the root      |
| `hostname mismatch`                      | The name requested is not in the certificate's SAN list               |
| `self signed certificate`                | Internal CA not trusted by this client, or an interception proxy      |
| `no shared cipher`                       | Client and server support no common suite — usually a very old client |
| `handshake failure` on some clients only | Missing SNI, or a TLS version mismatch                                |

###### The chain , and the failure that only breaks non-browser clients

``` text
# what the server ACTUALLY sends - this is the whole diagnostic
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null
# Certificate chain
#  0 s:CN=api.example.com          <- leaf, yours
#    i:CN=R3, O=Let's Encrypt
#  1 s:CN=R3, O=Let's Encrypt      <- INTERMEDIATE. Must be served.
#    i:CN=ISRG Root X1
#                                  <- root is NOT sent; the client has it
# Verify return code: 0 (ok)

# THE COMMON FAILURE: the intermediate is missing.
#  0 s:CN=api.example.com
#    i:CN=R3, O=Let's Encrypt
# Verify return code: 20 (unable to get local issuer certificate)
```

``` text
  WHY "IT WORKS IN THE BROWSER" IS THE MOST MISLEADING SYMPTOM IN TLS

    a chain must be:  leaf -> intermediate(s) -> root

    the SERVER must send the leaf AND the intermediates.
    the CLIENT already has the root.

    if the intermediate is missing:

      BROWSERS      often succeed. They cache intermediates from other
                    sites, and follow the "AIA" URL in the certificate
                    to FETCH the missing one. Chrome and Firefox do
                    this silently.

      API CLIENTS   FAIL. .NET, curl, Java, Python, Go do not fetch
                    intermediates. They validate what was sent.

    so the report is always: "the website is fine, but our integration
    partner cannot connect" - and everyone spends an hour looking at
    the partner's code.

    the test that settles it in ten seconds, from a clean machine:
      openssl s_client -connect host:443 | grep 'Verify return code'
```

| Verify code | Meaning                  | Fix                                                            |
|-------------|--------------------------|----------------------------------------------------------------|
| 0 (ok)      | Valid                    | —                                                              |
| **20 / 21** | **Missing intermediate** | Serve the full chain — usually `fullchain.pem`, not `cert.pem` |
| 10          | Expired                  | Renew — and fix the automation that should have                |
| 18          | Self-signed              | Expected internally; add to the trust store deliberately       |
| 62          | Hostname mismatch        | SAN does not cover the name requested                          |
| 19          | Self-signed in chain     | A corporate TLS-inspection proxy                               |

Two operational notes. **SNI** is sent in the ClientHello *before* encryption, so the server knows which certificate to present when several share an IP — a client that omits SNI gets the default certificate and a name mismatch. And **expiry monitoring must be external**: check from outside, on a schedule, alerting at 30 and 14 days. Renewal automation that silently stops is the single most common cause of a certificate outage, and the automation cannot alert you that it is broken.

#### Certificates in practice

| Concern                       | Approach                                                                     |
|-------------------------------|------------------------------------------------------------------------------|
| Public certificates           | ACME (Let's Encrypt, ZeroSSL) — free, automated, 90-day, renewed at 60       |
| Internal service certificates | An internal CA: step-ca, Vault PKI, or your cloud's private CA               |
| Wildcards                     | `*.example.com` — covers one level only, and needs DNS validation            |
| Where to terminate            | At the load balancer or ingress, normally. Managed there, not on each server |
| Renewal                       | **Fully automated.** Any manual step will eventually be missed               |
| Monitoring                    | External expiry checks — not from the system doing the renewing              |
| Rotation without downtime     | Reload, do not restart. nginx and most proxies reload config gracefully      |

``` text
# ACME with DNS validation - required for wildcards, and works for hosts
# with no inbound internet access
certbot certonly --dns-route53 -d '*.example.com' -d example.com

# Kubernetes: cert-manager handles issuance and renewal declaratively
apiVersion: cert-manager.io/v1
kind: Certificate
spec:
  secretName: api-tls
  dnsNames: [api.example.com]
  issuerRef: { name: letsencrypt-prod, kind: ClusterIssuer }
```

``` csharp
# mutual TLS: the client also presents a certificate.
# the strongest service-to-service authentication available, and the reason
# service meshes are attractive - they issue, rotate and enforce it for you.

# nginx
ssl_client_certificate /etc/ssl/internal-ca.crt;
ssl_verify_client on;
ssl_verify_depth 2;

# the operational cost people underestimate: every service now needs a
# certificate, and every certificate needs rotating. Without automation,
# mTLS becomes an outage generator rather than a security control.
```

> **\[Note\]**
>
> **The failure that recurs everywhere.** Certificate expiry causes a large share of avoidable outages, and it is entirely preventable. Automate renewal, monitor expiry *from outside* the renewing system, alert well before the deadline, and include certificates in your inventory. The mode to defend against is a certificate on a forgotten server that nobody knew existed until it expired on a Sunday.
