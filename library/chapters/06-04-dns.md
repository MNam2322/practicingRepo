# 6.4 DNS

> **Quick look.** DNS turns names into addresses through a distributed, heavily cached directory.
>
> - Recursive resolvers walk a tree of zones from the root and cache every answer.
> - Record types: A/AAAA for addresses, CNAME for aliases, MX for mail, TXT for text.
> - Every record has a TTL; lower it before planned changes, because cached copies outlive edits.
> - Pooled HTTP connections never re-resolve: set PooledConnectionLifetime or use IHttpClientFactory.
> - DNS failures often look like something else, and DNS is not instant failover.


### The big picture

People remember names like `example.com`. Networks deliver packets to numbers like `93.184.215.14`. DNS, the Domain Name System, is the service that turns one into the other. It is like a phone book for the whole internet, except that no single book exists: the directory is split across millions of servers, each responsible for its own part, with answers cached along the way.

Almost every network connection your code makes starts with a DNS lookup, so DNS problems show up everywhere, often disguised as something else. This chapter explains how a name is looked up step by step, and what kinds of records DNS holds. It also explains why a change you make can take hours to reach everyone, and why a long-running .NET service can keep talking to an old server after the address has changed.

### Skip check

Answer each question in your head, then read the answer under it. If you got all of them, you can skip this chapter.

**1. What does a recursive resolver do?**

> It answers lookups on behalf of your machine. If the answer isn't in its cache, it asks a root server who handles `.com`, then asks that server who handles `example.com`, then asks that server for the address. It caches every answer.

**2. What is the TTL on a DNS record?**

> How many seconds resolvers and clients may cache the answer before asking again. A record with a TTL of 3600 may be served from caches for up to an hour after it changes.

**3. What are A, AAAA, CNAME, MX and TXT records?**

> A gives an IPv4 address, and AAAA an IPv6 address. CNAME says a name is an alias for another name, and MX names the mail servers for a domain. TXT holds free text, used for things like domain ownership checks and email security rules.

**4. You changed a DNS record an hour ago. Why do some users still reach the old server?**

> Their resolvers cached the old answer and will keep using it until its TTL runs out. Some software caches even longer. Lower the TTL well before a planned change.

**5. Why can a .NET service keep sending requests to an old IP address after DNS has changed?**

> HttpClient reuses pooled connections, which stay connected to the old address and never look the name up again. Setting `PooledConnectionLifetime` on the handler makes connections retire and reconnect, with a fresh lookup.

**6. Is DNS traffic encrypted by default?**

> No. Classic DNS is plain UDP on port 53, readable and forgeable by anyone on the path. DNS over HTTPS and DNS over TLS encrypt it, and DNSSEC signs records so forgeries can be detected.

**7. In Kubernetes, why can looking up "api.example.com" cause several failed queries first?**

> Resolvers in pods are configured with search domains and a rule to try them first for names with few dots. The resolver tries `api.example.com.default.svc.cluster.local` and similar names before the real one. A trailing dot, `api.example.com.`, skips the search list.

### Names for people, numbers for machines

Every connection in TCP and UDP (6.3) needs an IP address. People, and configuration files, use names instead. Names are easier to remember, and they can stay the same when servers move to new addresses.

**DNS**, the Domain Name System, maps names to addresses and other information. It was designed in 1983 to replace a single shared file of every host on the early internet, which had grown too big to copy around. Today it is one of the largest distributed systems in the world, answering trillions of queries a day.

### The shape of a name

A **domain name** such as `www.example.com` is read from right to left. Each part, separated by dots, is a label, and each label is a level in a tree.

At the top is the root, written as an empty label: strictly, the name is `www.example.com.` with a final dot, though that dot is almost always left off. Below the root are the **top-level domains** (TLDs): generic ones such as `.com`, `.org` and `.aero`, and country ones such as `.uk`, `.de` and `.au`. Below each TLD are the domains registered by organizations, such as `example.com`. Below those are any names the organization creates: `www.example.com`, `api.example.com`, `mail.example.com`.

The tree is split into **zones**: parts of the tree managed by one organization. The owner of `example.com` runs, or pays someone to run, the servers that answer for everything in the `example.com` zone.

### Who knows the answer

No server knows every name. Instead, responsibility is passed down the tree. This is called **DNS delegation**. It is unrelated to delegation between objects in Composition and dependency injection (4.3). The root servers know which servers handle each TLD. The `.com` servers know which servers handle `example.com`. The `example.com` servers know the actual addresses.

The servers that hold the real, official records for a zone are its **authoritative name servers**. They answer only for their own zones.

There are 13 named root server identities, run by 12 organizations, but each one is really hundreds of machines spread around the world sharing one address. A packet to that address is delivered to whichever copy is nearest, a routing technique called **anycast**. Public resolvers such as Cloudflare's `1.1.1.1` and Google's `8.8.8.8` use anycast in the same way.

### Looking a name up

When a program on your machine needs the address of `api.example.com`, several parties are involved.

The program asks the operating system. The part of the OS that does this is called the stub resolver. It checks the **hosts file**, a small local file that overrides DNS for chosen names, `/etc/hosts` on Linux and macOS and `C:\Windows\System32\drivers\etc\hosts` on Windows. It checks its own cache. If neither has the answer, it sends the question to a configured resolver, usually one supplied by DHCP from the network, as IP addresses and routing (6.2) described.

That resolver is a **recursive resolver**: it does the whole job of finding the answer on the client's behalf. It is run by your ISP, your company, your cloud provider or a public service. If the answer isn't in its cache, it works down the tree. It asks a root server, "where is `api.example.com`?". The root replies, "I don't know, but here are the servers for `.com`". It asks a `.com` server, which replies with the servers for `example.com`. It asks one of those, which gives the address. The resolver caches every step and returns the address to your machine.

With a cold cache, that is three or four round trips to servers around the world. With a warm cache, which is the normal case for popular names, it is one quick round trip to the resolver, or nothing at all when the answer is already cached locally.

### Records

A zone holds **DNS records**. Each has a name, a type, a time to live and a value. The common types are these.

An **A record** gives an IPv4 address. An **AAAA record**, pronounced "quad-A", gives an IPv6 address. A name can have several of either, for several servers.

A **CNAME record**, for "canonical name", says that a name is an alias for another name: `www.example.com` is really `example-web.cloudhost.net`. The resolver then looks up that name instead. Cloud services use CNAMEs heavily, so you can point your own names at their changing infrastructure. A name with a CNAME can't have any other records, which is why the bare domain, `example.com` itself, can't be a CNAME. Many DNS providers offer a workaround, often called an alias or flattening.

An **MX record** names the mail servers that accept email for the domain. A **TXT record** holds text. It is used to prove you own a domain to services like certificate authorities and email providers, and to publish email security rules. An **NS record** names a zone's authoritative servers. An **SRV record** gives the host and port for a named service. A **CAA record** says which certificate authorities may issue certificates for the domain, as TLS (6.5) explains.

### Caching and TTL

Every record carries a time to live, in seconds: the **record TTL**. Resolvers and clients may reuse a cached answer until it expires. It is the same idea as the time to live in IP packets from IP addresses and routing (6.2), applied to how long an answer stays fresh.

Caching is what makes DNS fast and able to handle its load. It is also why DNS changes aren't instant. If a record has a TTL of 86,400 seconds, a day, some resolvers will keep serving the old answer for up to a day after you change it. People call this "propagation", but nothing is being pushed out; old copies are simply expiring.

The practical routine for moving a service is simple. Days before the move, lower the TTL to something short, such as 60 or 300 seconds. Wait for the old, long TTL to expire. Make the change. Raise the TTL again once everything is settled.

Failed lookups are cached too. When a name doesn't exist, the answer, NXDOMAIN for "non-existent domain", is cached for a while. This is **negative caching**. If a program looks up a name before it has been created, the "doesn't exist" answer can linger after you add it.

```csharp
// dns.cs — run with: dotnet run dns.cs   (the second part needs an internet connection)
using System.Buffers.Binary;
using System.Linq;
using System.Net;
using System.Net.Sockets;
using System.Text;

// 1. The usual way: ask the operating system's resolver
foreach (string name in new[] { "localhost", "example.com", "no-such-host.invalid" })
{
    try
    {
        IPAddress[] addresses = await Dns.GetHostAddressesAsync(name);
        Console.WriteLine($"{name}: {string.Join(", ", addresses.Select(a => a.ToString()))}");
    }
    catch (SocketException ex) { Console.WriteLine($"{name}: {ex.SocketErrorCode}"); }   // HostNotFound
}
// localhost: 127.0.0.1 (and often ::1)
// example.com: one or more public addresses
// no-such-host.invalid: HostNotFound   (.invalid is reserved never to exist)

// 2. The same question built by hand and sent straight to a public resolver over UDP
byte[] query = BuildQuery("example.com", id: 0x1234);
Console.WriteLine($"query: {query.Length} bytes {Convert.ToHexString(query)}");
// query: 29 bytes 123401000001000000000000076578616D706C6503636F6D0000010001
using var udp = new UdpClient();
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(3));
try
{
    await udp.SendAsync(query, new IPEndPoint(IPAddress.Parse("1.1.1.1"), 53), timeout.Token);
    UdpReceiveResult reply = await udp.ReceiveAsync(timeout.Token);
    foreach (var (address, ttl) in ReadAnswers(reply.Buffer))
        Console.WriteLine($"example.com has address {address}, cacheable for {ttl} seconds");
}
catch (OperationCanceledException) { Console.WriteLine("no reply within 3 seconds (some networks block direct DNS)"); }

static byte[] BuildQuery(string name, ushort id)
{
    var bytes = new List<byte>();
    byte[] header = new byte[12];
    BinaryPrimitives.WriteUInt16BigEndian(header, id);          // an id, echoed back so replies can be matched
    header[2] = 0x01;                                           // flags: "recursion desired", do the whole lookup
    BinaryPrimitives.WriteUInt16BigEndian(header.AsSpan(4), 1); // one question follows
    bytes.AddRange(header);
    foreach (string label in name.Split('.'))                   // "example.com" becomes 7 example 3 com 0
    {
        bytes.Add((byte)label.Length);
        bytes.AddRange(Encoding.ASCII.GetBytes(label));
    }
    bytes.Add(0);                                               // the empty root label ends the name
    bytes.AddRange(new byte[] { 0, 1, 0, 1 });                  // type 1: A record; class 1: internet
    return bytes.ToArray();
}

static List<(IPAddress Address, uint Ttl)> ReadAnswers(byte[] m)
{
    int count = BinaryPrimitives.ReadUInt16BigEndian(m.AsSpan(6));   // how many answers the reply holds
    int pos = SkipName(m, 12) + 4;                                   // skip the echoed question: name, type, class
    var found = new List<(IPAddress Address, uint Ttl)>();
    for (int i = 0; i < count; i++)
    {
        pos = SkipName(m, pos);
        ushort type = BinaryPrimitives.ReadUInt16BigEndian(m.AsSpan(pos));
        uint ttl = BinaryPrimitives.ReadUInt32BigEndian(m.AsSpan(pos + 4));
        ushort length = BinaryPrimitives.ReadUInt16BigEndian(m.AsSpan(pos + 8));
        pos += 10;
        if (type == 1 && length == 4) found.Add((new IPAddress(m.AsSpan(pos, 4)), ttl));
        pos += length;                                               // skip other record types, such as a CNAME
    }
    return found;
}

static int SkipName(byte[] m, int pos)
{
    while (true)
    {
        byte length = m[pos];
        if (length == 0) return pos + 1;                   // end of the name
        if ((length & 0xC0) == 0xC0) return pos + 2;       // two top bits set: a pointer to a name used earlier
        pos += 1 + length;
    }
}
```

The reply reuses names it has already written, with a two-byte pointer back to the first copy, to keep packets small. That is why `SkipName` checks the top two bits of each length byte, using the masks from Bits and bytes (1.1).

### DNS in your programs

In .NET, `Dns.GetHostAddressesAsync` asks the operating system's resolver, and every `HttpClient` request, database connection and message client does the same thing underneath. Two behaviours catch people out.

First, long-lived connections don't look names up again. `HttpClient` keeps connections in its pool, as TCP and UDP (6.3) described. A connection opened last week is still connected to last week's address, however many times DNS has changed since. Set `PooledConnectionLifetime` on `SocketsHttpHandler`, for example to a few minutes, so connections retire and reconnect with a fresh lookup. `IHttpClientFactory` handles this by rotating its handlers every two minutes by default.

Second, lookups can be slow and can fail. A resolver that doesn't answer makes the operating system wait several seconds before trying again. A service that looks up a name on every request, with no caching, turns every DNS hiccup into slow requests.

### DNS in containers and Kubernetes

Containers usually get DNS settings from their platform, through a file called `/etc/resolv.conf`. In Kubernetes, every service gets a DNS name such as `orders.default.svc.cluster.local`, and a cluster DNS server answers for them. That is how services find each other without knowing addresses.

Kubernetes also configures **search domains**: suffixes the resolver tries adding to short names, so a pod can refer to `orders` instead of the full name. By default it tries them first for any name with fewer than five dots. A lookup for `api.example.com` becomes several failed lookups of names like `api.example.com.default.svc.cluster.local` before the real one. For services that call external names a lot, that adds latency and load. Writing the name with a trailing dot, `api.example.com.`, tells the resolver it is complete.

### Spreading load and surviving failure

DNS is often used to direct traffic. A name with several A records spreads clients across several servers, because different clients pick different addresses. Managed DNS services can answer differently depending on where the client is, to send users to the nearest region, or stop returning an address whose health checks fail.

All of this is limited by caching. Clients keep using a cached address until its TTL expires, and some ignore TTLs altogether. DNS moves traffic gradually, not instantly, which is why fast failover usually happens at a load balancer rather than in DNS alone.

### Security

Classic DNS is unencrypted UDP on port 53. Anyone on the path can see which names you look up, and an attacker who can send packets to a resolver can try to plant forged answers in its cache, called cache poisoning. Randomized query ids and ports make that much harder, and there are two further defences.

**DNSSEC** adds digital signatures to records, so a resolver can check that an answer really came from the zone's owner and wasn't altered. Signatures are explained in TLS (6.5). Adoption is patchy, and a misconfigured signature makes a whole domain disappear for resolvers that check.

**Encrypted DNS** protects lookups from being read or altered on the way to the resolver: DNS over HTTPS (DoH) and DNS over TLS (DoT). Browsers and operating systems increasingly use it by default. It hides lookups from the local network, but the resolver itself still sees them.

### When things break

Among operations teams, "it's always DNS" is a running joke with a lot of truth in it. An expired domain registration, a mistaken record, a delegation that points at the wrong servers or an unreachable resolver makes everything that depends on those names fail at once, with error messages that often don't mention DNS at all. When many unrelated things break together, check name resolution early.

### In short

DNS turns names into addresses using a tree of zones, each answered by its own authoritative servers. A recursive resolver walks the tree from the root on your behalf and caches every answer. Records come in types: A and AAAA for addresses, CNAME for aliases, MX for mail, TXT for text. Every record has a TTL, so changes reach users only as cached copies expire; lower TTLs before planned changes. Pooled connections never re-resolve names, so set `PooledConnectionLifetime` or use `IHttpClientFactory`, and remember that classic DNS is neither private nor tamper-proof.

### What goes wrong

**Changing records with long TTLs.** A migration takes a day to reach everyone, and some users hit the old servers long after they are switched off. Lower TTLs days before the change.

**Connections that outlive DNS changes.** A service keeps sending traffic to an old address after a failover. Set `PooledConnectionLifetime`, or use `IHttpClientFactory`.

**Caching "not found".** A lookup made before a record existed keeps failing for a while after it is added. Wait out the negative-caching time, or flush caches where you control them.

**Slow lookups in hot paths.** Code that resolves names on every call, with no caching, adds latency and fails whenever the resolver stutters. Let the OS or a connection pool cache, and keep timeouts short.

**Search domain overhead in Kubernetes.** External names trigger several failed internal lookups first. Use fully qualified names with a trailing dot, or tune the pod's DNS settings.

**Forgotten renewals.** An expired domain registration or a lapsed DNS hosting account takes everything down at once. Put renewals on automatic, and monitor expiry dates.

**Relying on DNS for instant failover.** Clients cache addresses and some ignore TTLs entirely, so traffic keeps flowing to a dead server. Use load balancers or client-side retries across several addresses.

### Cost model

A lookup answered from the operating system's cache costs microseconds. One answered from the resolver's cache costs one round trip to the resolver, typically 1 to 20 ms. A lookup with a cold cache walks the tree and can take 50 to 200 ms. A resolver that doesn't reply can cost seconds, because the OS waits before retrying. A DNS query and answer are each typically under 512 bytes, one UDP packet each. With sensible TTLs and connection reuse, DNS costs almost nothing per request, which is why the failures are what hurt.

### In other languages (optional)

**JavaScript and TypeScript.** Node.js has `dns.lookup`, which uses the OS resolver and its thread pool, and `dns.resolve` functions, which query DNS servers directly. Browsers resolve names themselves and don't expose DNS to pages.

**Python.** `socket.getaddrinfo` uses the OS resolver. The `dnspython` library queries DNS servers and handles every record type.

**Command line.** `nslookup example.com` works everywhere, and `dig example.com` on Linux and macOS shows every detail, including TTLs. `dig +trace example.com` walks down from the root just as a recursive resolver does.

### Key terms

- **DNS**: Domain Name System: the distributed directory that turns names into addresses and other records.
- **Domain name**: A name such as www.example.com, made of labels read from right to left.
- **Top-level domain**: The last label of a domain name, such as .com, .aero or .uk. Often shortened to TLD.
- **Zone**: The part of the DNS tree managed by one organization.
- **DNS delegation**: Passing responsibility for part of the DNS tree down to other servers.
- **Authoritative name server**: A server that holds the official records for a zone.
- **Anycast**: Giving many servers the same address, so each packet goes to the nearest one.
- **Hosts file**: A small local file that maps names to addresses, checked before DNS.
- **Recursive resolver**: A server that finds answers on a client's behalf, walking the DNS tree and caching the results.
- **DNS record**: One entry in a zone: a name, a type, a TTL and a value.
- **A record**: A DNS record giving an IPv4 address.
- **AAAA record**: A DNS record giving an IPv6 address.
- **CNAME record**: A DNS record saying a name is an alias for another name.
- **MX record**: A DNS record naming a domain's mail servers.
- **Record TTL**: How many seconds a DNS answer may be cached.
- **Negative caching**: Caching the answer that a name doesn't exist.
- **Search domain**: A suffix a resolver tries adding to short names before looking them up as written.
- **DNSSEC**: Digital signatures on DNS records, so forged answers can be detected.
- **Encrypted DNS**: DNS lookups sent over encrypted connections, as DNS over HTTPS or DNS over TLS.

### In practice: realistic examples

2 worked scenarios of the kind you meet at work: the situation, what goes wrong, the code that fixes it, and the lesson.

#### Example 1: A database failover that apps ignored for 10 minutes

The database fails over to a new IP, but services keep connecting to the old one.

**What goes wrong.** The DNS record had a 600-second TTL and the HTTP client pooled connections indefinitely.

*Re-resolve regularly*

```csharp
builder.Services.AddHttpClient<OrdersClient>()
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(2),   // connections retire, names are looked up again
    });
// and lower the record's TTL (e.g. to 60 s) a day before planned changes
```

> **Lesson:** Caches at every level hold old DNS answers. Plan TTLs and connection lifetimes for failover.

#### Example 2: Moving a domain to a new host without downtime

The booking site moves to a new load balancer IP next week.

*A safe sequence*

```text
T-2 days  lower TTL on book.example.com from 3600 to 60
T-0       new load balancer serving traffic in parallel (old one still up)
T-0       switch the A/AAAA record to the new IP
T+1 hour  watch traffic drain from the old balancer
T+2 days  remove the old balancer, raise TTL again
```

> **Lesson:** DNS changes reach users only as caches expire. Lower the TTL in advance and run old and new side by side.

#### DNS

`api.example.com` is for humans. The network needs `93.184.216.34`.

DNS resolves the former to the latter, via a recursive walk: root servers → `.com` servers → `example.com`'s nameservers. Results are cached at every level according to their **TTL**.

Two consequences that bite in production:

- **Resolution costs time.** First request to a new host pays 20–100 ms before a single byte of HTTP moves. Cached afterward.
- **Caching outlives changes.** Point a DNS name at a new IP and clients keep using the old one until their cache expires. .NET's `SocketsHttpHandler` caches connections indefinitely by default, so a long-lived `HttpClient` can hold a stale IP forever. `PooledConnectionLifetime` exists to fix precisely this.

#### DNS: the lookup you never see

Nothing on the network routes by name. Before any connection, `api.example.com` must become an IP address — a separate network operation, usually invisible in your code and your traces.

``` text
  app ──► OS resolver ──► recursive resolver (ISP / cloud / 8.8.8.8)
                              ├─► root servers:  "ask the .com servers"
                              ├─► .com servers:  "ask example.com's servers"
                              └─► authoritative: "93.184.216.34, TTL 300"
  Cached at every level for TTL seconds.
  A cache hit is sub-millisecond; a full resolution can be 20-100 ms.
```

| Record       | Holds                                            |
|--------------|--------------------------------------------------|
| `A` / `AAAA` | an IPv4 / IPv6 address                           |
| `CNAME`      | an alias to another name — costs an extra lookup |
| `SRV`        | host *and port* for a named service              |
| `TXT`        | arbitrary text — SPF, domain verification        |

> **\[Trap\]** **The classic .NET DNS bug.** A `static HttpClient` is correct advice — it avoids socket exhaustion — but a long-lived `HttpClient` keeps its connections open indefinitely and therefore **never re-resolves DNS**. When the target fails over to a new IP, your service keeps dialling the old one until it is restarted. Set a connection lifetime so pooled connections are periodically retired and the name resolved again:
>
> ``` csharp
> services.AddHttpClient<IOrderApi, OrderApi>()
>     .SetHandlerLifetime(TimeSpan.FromMinutes(2));      // IHttpClientFactory
> // or directly:
> new SocketsHttpHandler { PooledConnectionLifetime = TimeSpan.FromMinutes(2) };
> ```

> **\[Tip\]**
>
> **A failing deploy that "only affects some pods" is often DNS caching.** TTLs are honoured inconsistently by resolvers, containers, and application-level caches, so after a failover different instances hold different answers for minutes. When behaviour is inconsistent across identical instances, check what each one resolved before checking the code.

#### DNS, end to end

DNS failures are responsible for a remarkable share of outages, largely because caching means the failure and the symptom are separated in time.

``` text
  resolving api.example.com, from cold

  1  your process   ->  stub resolver (glibc / systemd-resolved)
  2  check /etc/hosts and the local cache
  3  ask the configured resolver (/etc/resolv.conf)
  4  recursive resolver asks:
       ROOT servers      "who handles .com?"
       .com TLD servers  "who handles example.com?"
       example.com NS    "what is api.example.com?"
  5  answer returned, CACHED at every layer for TTL seconds

  the caching is the operational problem:
    change a record with a 3600s TTL and some clients use the old value
    for an hour - including some that ignore TTL entirely.
    LOWER THE TTL DAYS BEFORE a planned cutover, then raise it after.
```

| Record                | Maps                                | Note                                                                             |
|-----------------------|-------------------------------------|----------------------------------------------------------------------------------|
| **A**                 | Name → IPv4                         |                                                                                  |
| **AAAA**              | Name → IPv6                         |                                                                                  |
| **CNAME**             | Name → another name                 | **Cannot coexist** with other records at the same name, so not valid at the apex |
| **ALIAS** / **ANAME** | Apex → another name                 | Provider-specific workaround for the CNAME-at-apex problem                       |
| **MX**                | Domain → mail servers               | With priorities                                                                  |
| **TXT**               | Arbitrary text                      | SPF, DKIM, domain-ownership verification                                         |
| **NS**                | Zone → its authoritative servers    | Delegation                                                                       |
| **SRV**               | Service → host and port             | Used by service discovery                                                        |
| **CAA**               | Which CAs may issue for this domain | Worth setting; blocks mis-issuance                                               |

| DNS problem                            | Cause                                                                               |
|----------------------------------------|-------------------------------------------------------------------------------------|
| Works on my machine, not on the server | Different resolvers, or a private zone the server cannot see                        |
| Change did not take effect             | TTL caching — at the client, the resolver, or the application                       |
| Intermittent resolution failures       | One authoritative server unhealthy, or UDP responses over 512 bytes being truncated |
| Works by IP, not by name               | DNS only — the network path is fine                                                 |
| Slow first request, then fast          | Resolution cost on a cold cache                                                     |
| Java resolves once and never again     | The JVM historically cached DNS forever; set `networkaddress.cache.ttl`             |

> **\[Trap\]**
>
> **Common trap.** Applications that resolve a hostname once at startup and cache the IP forever will not follow a failover. This affects connection pools, HTTP clients holding keep-alive connections, and several runtimes' default behaviour. If your DR plan is “repoint DNS”, verify that your *clients* actually re-resolve — test it, do not assume it.

###### A resolution, traced, and the caching layers that lie to you

``` text
# trace the full delegation chain from the root - what a resolver does
dig +trace api.example.com
# .            NS a.root-servers.net.        <- root
# com.         NS a.gtld-servers.net.        <- TLD
# example.com. NS ns1.example.com.           <- authoritative
# api.example.com. 60 IN A 203.0.113.10      <- the answer, TTL 60

# ask ONE specific resolver, bypassing every cache in between
dig @8.8.8.8 api.example.com
dig @10.0.0.2 api.example.com          # the VPC resolver
dig @127.0.0.53 api.example.com        # systemd-resolved, locally

# and what the TTL is doing RIGHT NOW - a countdown means a cached answer
dig api.example.com | grep -A1 'ANSWER SECTION'
# api.example.com. 37 IN A 203.0.113.10       <- 37s left of a 60s TTL
```

``` text
  FOUR CACHES BETWEEN YOU AND THE TRUTH, and each can disagree

    1  the APPLICATION            .NET, the JVM, a connection pool
    2  the OS stub resolver       systemd-resolved, nscd
    3  the RECURSIVE resolver     your VPC resolver, or 8.8.8.8
    4  intermediate resolvers     ISP, corporate

  so "I changed the DNS record and it still resolves to the old IP"
  has four possible answers, and you find out which by asking each
  layer separately with the dig commands above.

  THE TTL TRAP AROUND A MIGRATION

    a record with a 24-hour TTL cannot be changed quickly. Lowering the
    TTL does not help at cutover - the OLD, LONG TTL is already cached
    everywhere.

    so the sequence must be:
      T-48h   lower the TTL to 60s and PUBLISH
      T-24h   old caches expire; everyone now honours 60s
      T-0     change the record. Propagation takes ~60s.
      T+1h    raise the TTL again

    skipping the first step is why cutovers "take a day to propagate".

  and the .NET-specific one: a POOLED CONNECTION never re-resolves.
  DNS is consulted when a connection is OPENED, not per request. A
  static HttpClient with default settings can hold a connection to a
  dead IP indefinitely -> PooledConnectionLifetime bounds it.
```

| Record            | Does                        | Watch for                                                                      |
|-------------------|-----------------------------|--------------------------------------------------------------------------------|
| `A` / `AAAA`      | Name → IPv4 / IPv6          | Missing AAAA on a dual-stack client causes a slow fallback                     |
| `CNAME`           | Name → another name         | Cannot coexist with other records at the same name; not allowed at a zone apex |
| `ALIAS` / `ANAME` | CNAME-like, at the apex     | Provider-specific, resolved server-side                                        |
| `SRV`             | Service → host and **port** | How Kubernetes and Consul publish services                                     |
| `TXT`             | Arbitrary text              | SPF, DKIM, domain-ownership proofs                                             |
| `NS`              | Delegation                  | A mismatch with the parent causes intermittent failures                        |
| `CAA`             | Which CAs may issue for you | Blocks certificate issuance if wrong                                           |
